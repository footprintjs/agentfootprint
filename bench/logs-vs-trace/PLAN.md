# Registered boundary: deterministic preparation only

## Question for a later study

For the same planted defect and completed execution, does access to bounded
record-navigation tools change independently checked fixes or measured model
usage compared with a declared ordinary-log baseline?

The current implementation verifies study plumbing only. No live-model study is
enabled or authorized by this plan, and the scripted results answer no part of
that empirical question.

## Preparation delivered here

One synthetic unit mismatch, a correct-code control and a missing-record control
exercise both evidence arms. A fixed seed records paired arm order. Ordinary logs
are intentionally small, structured stage messages, not an inflated full-trace
dump. The trace arm calls existing public tools over the same completed native
run. No alternative production API or experiment framework is added.

Candidate corrections are data: keep the current denominator, use annual income,
or use monthly income. They are never evaluated as JavaScript. A private oracle
replays unseen income, debt, policy-boundary and credit controls. Keeping already
correct code is a passing control; it is not counted as a repaired defect.
Malformed candidates and missing evidence have explicit dispositions. Tests
cross-check the native fixture and the independent replay policy so two copied
implementations cannot silently agree on a wrong fallback.

Both arms have identical task wording, policy, input, candidate grammar and
completed run. Case labels, the planted defect and grading outcomes are excluded
from served task/evidence. Scripted transcripts are audit records, not blinded
model trials. Nothing here claims that this small synthetic case represents
production debugging work.

## Required before any model study

1. Obtain a fresh scope and hard spending limit, plus named models, provider and
   stop conditions. A separate reviewed implementation would add that route;
   this CLI has no paid escape hatch. Keys must remain outside reports and code.
2. Register a broader case sheet, baseline instrumentation, source-code access,
   tool bounds, maximum turns, timeout and the exact prompt/tool versions. Review
   baseline fairness before collecting comparative results.
3. Freeze held-out inputs and deterministic acceptance tests before runs. Record
   every attempted trial, refusal, timeout, missing record and unsupported answer;
   never silently discard an inconvenient trial or treat unknown as a pass.
4. Randomize paired order using a recorded seed and predeclare repetitions and
   the comparison rule. Keep arm labels and oracle data out of debugger inputs.
   Include unchanged controls and fixes that regress an independent control.
5. Read turns and provider input/output usage from actual run records and provider
   accounting. Retain usage provenance, prompt/cache accounting and prices used.
   Missing usage stays unknown; response characters cannot substitute for tokens.
6. Report paired fix outcomes and usage distributions with uncertainty and the
   registered denominator. Label any human judgement explicitly. No model grades
   another model's success, and scripted validation rates are not study results.

The historical request also mentions an orchestrator before/after token reading.
No such telemetry is available from this harness. It is not collected, and neither
chat length nor tool-response bytes supplies that measurement.

## Completion boundary

The no-cost plan, executable validation harness, recorded validation output and
automated tests complete this preparation phase. The empirical benchmark and its
claims remain pending the separate scope, budget, implementation and review above.

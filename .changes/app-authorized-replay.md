**You decide which MCP tool calls are sent again, and the run records what each attempt is known to have done.** `mcpClient({ replay })` takes your declaration for that server's tools: which failure kinds each tool may be sent again on (`on: ['throttle', 'network']`), which tools make changes (`changes: true`), and whether the server deduplicates by an idempotency key the call carries (`deduplicates: { argument }`). The permission comes only from you. The model, a tool's description and a server's annotations (`readOnlyHint`) never grant it. It is read once, when the client is built, and a field it does not know is refused there, so a misspelled `changes` cannot quietly turn the side-effect guard off.

A generic 429 does not prove the server ran nothing: RFC 6585 §4 defines it as rate limiting, and `Retry-After` says when to ask again, not that asking is safe. Under the new opt-in `policy: 'app-authorized'`, a 429 or a request that failed without an answer is sent again only for a tool your entry names. With no declaration, the 429 is returned and the record says why (`reason: 'not-permitted'`). A documented pre-execution refusal from the adapter you chose, AgentCore Runtime's session-busy reply, is still sent again within the budget, and its records name the guarantee. The adapter cites AWS's documentation for it.

**The default does not change in 11.x.** It is now named `policy: 'compatibility'`. A 429 is still sent again for every tool, on the assumption that the server refused it before running it. Every such retry records that assumption: `permission: { by: 'compatibility', assumes: 'refused-before-execution' }`, beside `effect: 'unknown'`. The assumption is never recorded as evidence that nothing ran. In the next major, `'app-authorized'` becomes the default. To keep today's behaviour then, write `replay: { policy: 'compatibility' }`. To move now, list each tool you want sent again on a 429 (`on: ['throttle']`), mark the tools that make changes, and declare `deduplicates` only for a server that honours the key.

**The side-effect guard is wired.** A tool you declare as making changes is never sent again automatically, under either policy, unless the server is declared to deduplicate by a key the call carries (`reason: 'changes-without-key'` otherwise). A key protects only when the server uses it. Before, the MCP retry used footprintjs's attempt runner without this guard, and only `retryOnThrottle: false` stopped a 429 retry of a tool with side effects.

**Every attempt in the saved run now carries three separate facts and its duration.** On each `agentfootprint.tools.request_attempts` row: the `failure` category, as before; `effect`, what is known about whether the attempt took effect (`none` only with a documented guarantee, named in `guarantee`; `unknown` for a 429, a lost connection, a timeout, a cut, a 5xx, a JSON-RPC error or a tool error; `applied` when the call completed, which is not proof that anything was written); `permission`, what allowed the next attempt (`by: 'declaration' | 'adapter' | 'compatibility'`); and `durationMs`. The `end` says how many requests were sent (`attempts`) and what is known of the whole series (`effect`). Uncertainty survives: once any attempt's effect is `unknown`, so is the series'. A later proven refusal does not resolve it, and a later success does not prove the operation happened only once. When the series sent a request again after an attempt of unknown effect, on your or an adapter's permission, and the call then does not complete, the call fails as "may have run": footprintjs's `UnknownEffectError`, with the call's own error as its `cause`, and the `end` says `mayHaveRun: true`. A request's record is now filed when its call settles, so an answered attempt's `effect` can say whether the call completed. A cancellation is still filed the moment it lands. A repeat re-sends the same request: the same arguments, server and session, as the same identity. A credential the library vends is still vended afresh for each attempt, for that same identity.

`ThrottleRetryInfo.kind` (`onRetry`) can now be `'network'`, for a repeat you declared after a request failed without an answer. The series' first rule reports it. `replay` is refused beside `connection`, whose transport this library did not build, and ignored for `stdio`. In dev mode, an entry for a tool the server does not list is named once per client.

**Code runners stop on time, and say what happened to a process they stopped.**

- `agentCoreCodeRunner`'s `execute` now honours `timeoutMs` and `signal`. It ignored both, so an aborted run kept waiting on the sandbox. The wait ends at the deadline with a `CodeSandboxError` (`reason: 'timed-out'`), which says the code may still be running in the session, or with the caller's own abort reason. One deadline covers the whole execution, including the setup call that exposes staged inputs.
- `localCodeRunner`'s timeout is now a real bound, and it stops the run's owned process group. The runtime's own timeout sent SIGTERM to the direct child and then waited. A child that ignored SIGTERM ran on, and if it then exited 0 the run came back as a success with its output cut at the deadline. A process the code or command had started kept running, and writing, after the caller was told it had been killed. Now, on POSIX, each run gets a process group of its own. At the deadline, on abort, at the 32 MiB output ceiling, and on an error reported after the start, the owned group is killed with SIGKILL at that moment, not after its pipes close. A timed-out or aborted call fails at once (`CodeSandboxError`, `reason: 'timed-out'`, for a command). This is cleanup, not containment: a descendant that starts its own session or group is outside the owned group, and a host killed before its exit handlers run cannot clean up. The local runner is still not a sandbox. The message says "its process group was killed" (it said "the process was killed"). On Windows, where there is no process group to signal, only the process itself is stopped, and the message says that work it started may still be running. Groups the runner still owns are killed when the host process exits. A timeout past about 24.8 days no longer fires after 1 ms.
- `localCodeRunner` no longer blames a missing interpreter for an aborted child ("could not run … (ABORT_ERR)"); the abort comes back as the caller's reason.
- Output past the 32 MiB buffer is no longer blamed on a missing interpreter either. It is a result: the output kept so far, the cut stated on `truncated`, no exit status, and `terminatedBy: 'SIGKILL'`.
- A child the operating system ended with a signal now has no `exitCode` instead of a made-up `1`, and `terminatedBy` names the signal (`ok` is still `false`).
- A failed child whose stderr was empty used to get the runtime's message ("Command failed: <the whole command line>") as its stderr, so the code itself reached the tool result. Now its stderr stays empty; the exit status line already says it failed.

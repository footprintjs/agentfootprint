---
type: breaking
---
**A person's decision now answers ONE paused request, once, for the exact call they were shown.** A consent gate (a tool's `checkIn`, a middleware's `ask`) mints a request id when it pauses — `CheckInRequest.id`, `MiddlewareAsk.id` — bound to the call that runs on approval: the tool, its arguments, the call id, the served party and, for an ask, where the chain resumes and the names of the rules from the asking link on. `checkInApproved({ request, by })` / `checkInDeclined({ request, by })` copy it into the new `CheckInDecision.requestId`, and a resume refuses, with the new `ResumeDecisionError` (`code: 'ERR_RESUME_DECISION'`, `reason`, `gate` — it never names a request id, in its message or on a field), a decision that:

- names no request (`'no-request'`) — built by an older release, or by hand;
- answers a pause that recorded none (`'request-not-recorded'`) — a checkpoint written before this release;
- names another request (`'other-request'`) — another conversation's, an earlier pause of the same run, a parallel sibling's;
- names this request for a call the checkpoint no longer holds (`'call-changed'`) — its arguments, tool, call id, party, chain position or the rules recorded after the ask were altered after the ask;
- answers a middleware ask on an agent whose `toolMiddleware` chain, from the asking link on, is not the one the person was asked under (`'chain-changed'`) — a later rule removed, added, renamed or moved by a redeploy is never skipped;
- was already used by a resume (`'already-answered'`) — approved or declined. The refusal says what that resume knows: it ran nothing, and whether the earlier resume finished — so whether the call ran — is not known there.

On approval the tool runs with a detached copy of exactly the arguments the person was shown (before, a resumed tool was handed a live view of the run's state, which later read the next pause's call). For a middleware ask, the links after the asking one still run and may still deny, but a link that hands back **different arguments** — a new object, or its copy edited in place — no longer has them run (the arguments are held to the request itself, and the tool runs on a fresh copy no link holds): the call is refused, the model reads why, and the record keeps the rewrite and a deny row. An ask whose arguments cannot be bound is recorded as that refusal, never as an `ask` row nobody answered.

Before this, any decision-shaped object answered any consent pause: a duplicate "approve" that arrived after the first had resumed the run approved the NEXT refund nobody was shown, a stored checkpoint whose arguments were edited after the ask still ran on the person's yes, and resuming the same checkpoint twice ran the tool twice. The tool never runs on a refusal. An agent's own `resume()` checks the caller's identity first, then refuses all but `'already-answered'` before anything moves; a request is spent where its decision is used, still before the tool — which is also where a composition's nested agents (`Sequence`, `Parallel`, …) are held to the rule, since a composition resumes them directly.

Answered requests are spent in a `DecisionLedger`, and **"once" holds per ledger**. By default every agent that names none shares one ledger in this process's memory — one per process even when an app loads both the CommonJS and the ESM build — so a server that builds an agent per request, a pool that rebuilds an evicted instance, or a composition's nested agents still answer each request once — in this process. That ledger grows by one id per answered request for the life of the process; it does not survive a restart and no other process sees it: when more than one process can resume the same paused run, give every agent that can resume it one ledger whose `spend(requestId)` is atomic in a store they all reach (`Agent.create({ decisionLedger })`), with an optional `isSpent(requestId)` so a host can tell a spend that never landed. The doors that keep a paused run (`standingAgent`, `streamHandler`) mark a stored pause answered (`PausedRun.answered`) when a resume of it fails after its decision may have been used — it reached a ledger: spent, refused as spent already, or a failed spend its ledger cannot say never landed — since the tool may have run; a resume that never took the decision to a ledger (refused, or abandoned because the caller hung up first) leaves the pause answerable. That is read from the library's own spend, never from an error's code or the decision object; a store that cannot be read while marking is marked anyway, and one that holds nothing (the session expired or was forgotten meanwhile) is left so. A resume abandoned while it waited — its caller already told the run ended — no longer spends the decision or runs the call afterwards. Once marked: a retry, a rebuilt instance, a restart or another host on the same store is refused with 409, the pending-question op reports nothing pending, and the next message continues the conversation the session stored — what the run kept mid-run under durable writes, else the conversation as of the pause — any call left open settled as unknown (under findings admission, `toolResultOrigin: 'outcome-unknown'`), and a call the person declined settled as declined (a decline never runs its call). Both doors read a stored session one way, so neither offers an answered pause for an answer; code that reads stored pauses itself with `readPausedRun` — a dashboard, a custom door — must honour `answered` the same way. Two processes receiving the same decision at the same moment both read the unmarked pause (the session store has no compare-and-set), a process that dies mid-resume marks nothing, and a store that refuses the mark's write leaves only this process's ledger refusing it (the door prints a warning): only a shared ledger closes those.

A consent pause no decision can ever answer no longer holds a hosted session: one stored by an earlier release (`'request-not-recorded'`), one whose call changed after the ask (`'call-changed'`), or an ask whose later rules a redeploy renamed, moved or removed (`'chain-changed'`). Both doors close it — the next message continues the conversation, every call it left open recorded for the model as not run ("That call did not run: the question it waited on could no longer be answered.") — and a decision for it is refused by name, runs nothing and closes it too (on `standingAgent`, a pause from an earlier release, whose question names no request, is closed by the next message instead); over AG-UI the answer ends the run cancelled, so the page's client lets the interrupt go. The pending-question op reports nothing pending for one the door can already tell is unanswerable.

`checkin.decision` events and `CheckInRecorder` decisions carry `requestId`, so the record joins each decision to the request it answered. A gated call whose arguments are not plain JSON (a `Date`, a `Map`, a non-finite number) cannot be bound and is refused at the gate — the tool does not run, nobody is asked, and the model reads why. Hosting doors answer `ERR_RESUME_DECISION` with 409; over AG-UI the page needs no change — the interrupt it answers is matched to the kept pause and the adapter names that pause's request.

What the binding is, and is not: it detects drift and replay — a checkpoint changed after the ask, a decision presented twice, to another pause, or to an agent with other rules. It does not defend against a hostile writer of the checkpoint store, who can rewrite the arguments together with the nonce and the request shown before the person decides, or switch the pause into a kind whose resume takes no decision (a credential-consent pause). Keep checkpoints server-side, or sign them, if the store is not trusted.

What breaks for code that builds or reads these values:

- `checkInApproved` / `checkInDeclined` require `request` — the paused request, with its `id` — and throw a `TypeError` without one. `CheckInDecision.requestId` is required.
- `isCheckInDecision(x)` returns `false` for a decision without `requestId`: an old-shaped `{ approved, by, at }` is no longer a decision (a resume refuses it as `'no-request'`).
- New required fields, for code that BUILDS these shapes (test doubles, fixtures, custom recorders, clients in other languages): `CheckInRequest.id`, `MiddlewareAsk.id`, `CheckInDecisionPayload.requestId` (the `agentfootprint.checkin.decision` event) and `CheckInDecisionRecord.requestId` (`CheckInRecorder`).
- A `toolMiddleware` link after an `ask` that rewrites the approved arguments no longer has its rewrite run — the call is refused. Put argument transforms before the asking link, so the person approves what will run.
- A paused ask resumes only on an agent whose chain, from the asking link on, has the same link names in the same order (`'chain-changed'`).
- The default ledger is one per process (it was one per agent): a decision already used is refused on a fresh agent in the same process too. Give an agent its own `inMemoryDecisionLedger()` only when it must not share.
- A nested agent's consent pause answered with something that is not a decision is refused (`DecisionRequiredError`) instead of becoming a `by: 'unknown'` decline.
- `LLMMessage.toolResultOrigin` gains `'outcome-unknown'`. `PausedRun` gains an optional `answered`: code that reads stored pauses itself (`readPausedRun`) must not offer a pause that has it for an answer — continue its `conversation` with the next message instead.

Migration: build every decision from the request the person was shown — `checkInApproved({ request: outcome.checkIn, by })` for a check-in, `checkInApproved({ request: outcome.ask, by })` for a middleware ask; on a hosted door, `request: pending.checkIn` / `pending.ask` from the `PendingAsk` the host replied with, sent as `decision`. A client that builds the decision JSON by hand adds `requestId: pending.checkIn.id` (or `pending.ask.id`). A plain `askHuman()` / `pauseHere()` pause is unchanged — its answer is a value.

Checkpoints and replicas: consent-gate checkpoints written by an earlier release cannot be answered (`'request-not-recorded'`) — before upgrading, drain them (answer every outstanding check-in and ask on the old release). One left over is closed on a hosted door by the next message, its call recorded as not run; carrying pauses yourself, abandon it and ask again. Do not run old and new replicas against the same stored pauses: a replica on an earlier release resumes a checkpoint written by this one without any binding (it ignores the request record and accepts any decision-shaped object), and a replica on this release refuses one written by an earlier one. Recommended order: (1) stop new consent pauses on the old release and drain or abandon the open ones; (2) move every replica that can resume a paused run to this release together; (3) clients: a server on this release needs `requestId`, and a pending ask from an earlier server carries no `id` — a client that sends `requestId` whenever the pending ask carries an `id` works against both (an earlier server ignores the field); `checkInApproved({ request })` needs the `id`, so use it on pending asks from this release. If more than one process can resume one paused run, give them a shared `decisionLedger` before relying on "once" across them.

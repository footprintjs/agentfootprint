**Skills work inside a signed thinking turn on the newest Claude models: every skill tool is listed from the first request, and a loaded body is the `read_skill` result.**
On a model whose thinking is bound to the context it was written under (`thinkingBinding` answers `bound`, or `unknown` for an id the adapter cannot place: Claude Haiku, Sonnet and Opus 5.5, Fable 5.1 and 5.2, Mythos 5.1 and 5.2, an application inference profile, a gateway alias, a deployment name, a newer id), a skill loaded in the middle of a tool turn was refused with `ContextChangedError`, because its body joined the system prompt and its scoped tools joined the tool list. The new `AgentOptions.skillContext` defaults to `'listed'` on such a model, so a skill load changes neither:

- every skill tool, scoped ones included, is on the tool list from the first request with a description that does not change, and `read_skill`'s description is the catalog for the whole run (it no longer names the graph cursor, the reachable set or the turn's menu; a refused pick's result still says where the graph can go);
- the body of any skill `read_skill` loads, a graph route or step target included, is that call's result. The system prompt leaves it out exactly while that result is in the history the request sends, so each request carries the body once. A window never drops that result while its skill is active (the new window refusal `'active-skill-body'`). With no such result (a history rewrite, a conversation paused before this change and resumed after it), the body is served in the system prompt as before;
- the body is exempt from `maxToolResultChars` and artifact placement, and every honesty reader treats it as the app's own text, exactly as the system-prompt body: the evidence gate does not count it as tool evidence, and the answer account records the skill as delivered;
- a tool whose declaring skills are all hidden from the caller's role (a permission checker that governs `skill_read`), scoped or not, is not listed, and a call to it is refused without naming the skill;
- **behaviour change:** a call to a scoped skill's tool before its skill is loaded is now refused with a fixed sentence naming the skill and the `read_skill` call that loads it, and the tool does not run. Before, such a call ran without being offered.

The choice is recorded as `skillContext` on the first `agentfootprint.stream.llm_start` of each run: the tool strategy and the body channel in the shared decision-record shape (`strategy`, `by`, `rule`, `label`, `reads`, `voucher`), and the binding answer that decided them. Listing every skill tool from the first request costs tool-list size on every request (30 scoped skills with two tools each are about 60 tools), which on an `unknown` id that is in fact unbound buys nothing. Every model the adapters place as unbound (OpenAI-family, Gemini, Ollama, mock, older Claude) keeps `'declared'` and its exact request and event bytes. Still refused by name inside a signed tool turn: a graph cursor that moves without a `read_skill` call (a declared edge), step narrowing, an `activeWhen` instruction, a tool provider whose list moves, and a window or summary that drops other turns. Not changed here: under `'declared'` an unscoped tool of a role-hidden skill stays on the tool list and runs when called by name.

Migration: two ways keep today's behaviour. For an agent whose model the adapter cannot place but the app knows to be unbound (an inference profile, a gateway alias, a deployment name), say so with the adapter's `thinkingBinding` option, for example `anthropic({ thinkingBinding: (id) => (id === 'my-gateway-alias' ? 'unbound' : undefined) })`: the default is then `'declared'`. To keep each skill's own `autoActivate` and `surfaceMode` on any model, pass `Agent.create({ ..., skillContext: 'declared' })`; on a bound model a skill load inside a signed tool turn is then refused by name as before.

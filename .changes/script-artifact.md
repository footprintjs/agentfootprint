**Show the script an answer was computed with — attached from the run record, and matched byte for byte when the model shows it.** A tool now declares that it runs a program (`script: { argument, language? }` on `defineTool`; `codeRunnerTool` declares it), and each call of it files the program it was handed and what its runner reported. `.scriptTravelsWithTheAnswer({ which, maxBytes })` attaches that recorded program under the answer — text after the `---` separator on a prose answer, data on `turn_end.scripts` always — so "always show the script" holds without the model retyping anything. `.namesAndNumbersFromEvidence({ code: 'match' })` reads a fenced block the model wrote as script content only when it equals, byte for byte after removing the Markdown wrapper, a program this turn's call submitted: no value candidates, labelled with that call's outcome; anything else stays prose, checked as before, and labelled `unmatched` (`evidence_checked.scripts`, each flagged value's `region`). Code is never evidence for a value. Labels say only what the record proves: `completed, exit 0` needs an explicit exit code; a bare runner verdict is "runner reported success/failure; no exit code"; a timeout, a cancellation or a service error with no exit code is "outcome unknown"; a tool that returned with no runner facts is "tool call returned; execution not confirmed". Under the answer layer an unmatched block reads "not sure" (`script-unmatched`), and the answer account says which script was shown or attached and what its call reported: five of each kind, then one "…and N more" line. A saved record's script fields are read back by one reader per shape — the one the checkpoint door uses — so a value no writer files (a label and an exit code that disagree, a count that is not a whole number) is counted unread and never becomes a line. An exit code is a whole number: a runner that reports anything else reported none. Bounded in UTF-8 bytes: 32,768 per program, 16 calls a turn, 32 blocks an answer, 4,000 attached by default; a program's text is kept for its own turn only. The match reads a block where a CommonMark renderer shows one: a block closes at a fence indented by up to three spaces, a lone CR ends a line, and reading stops at the first line where a renderer could pair fences another way. That is a fence indented inside a list, an HTML block, a `$$` math line, a closing fence with a trailing tab, or a block holding a fence run as long as its own fence. Everything after that point is prose. So a program cannot be shown in a way that carries a sentence past the block's close, unchecked. The audit chain's bounded mode replaces each attached program on `turn_end.scripts` with `'[N chars]'` and keeps its labels and counts. The attachment can never be taken into a block the answer left open: a fence the answer never closed is closed first (`turn_end.scripts.closedFence`), and after a line the library cannot vouch for (an indented fence, raw HTML, `$$`) the programs ride the data only (`turn_end.scripts.withheldFromText`). A tool's name and a call id in a library line are inline code with line breaks escaped. Each row belongs to a `dispatch`, the call's order within its turn: a reused provider id is a new call, a pause and its resume are one, and the per-turn bound counts dispatches. The program on a row is read just before the tool runs, and the facts a row attests are the dispatch's own: a runner files them into a slot on that call's context as well as into `codeRunsOf(tool)`, which is filled and emptied exactly as before. The `tools.code_run` event now also fires for a call that runs on the far side of a check-in, consent or ask pause. Without a redaction policy, an agent with neither option (and `code: 'check'`, the default) records the same events and state as before, with two differences on every agent. First, a code runner's call resumed after a pause now emits `agentfootprint.tools.code_run`, which it never did. Second, a `code_run` carries the facts of the dispatch that ran whenever the runner received that call's context (or a copy of it), so two runs that reuse a call id no longer trade them; a decorator that hands the runner a context of its own still gets the event, from the published map, as before. Under a redaction policy, the value-kind rule also keeps this feature's label words and record field names (for example `completed`, `dispatch`) wherever they appear, as it keeps every library word. The answer account's template set is 14.

The answer account and its show-me response are bounded by their complete serialized JSON size in UTF-8 bytes, including escaping and repeated pointers. Oversized listings retain their judgments and explicitly count omitted lines or facts; an account too large even without listings is marked unread. The response reserves space for its JSON frame.

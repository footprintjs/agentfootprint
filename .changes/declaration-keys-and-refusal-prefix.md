**`absent()`, `coverage()` and `semantic()` no longer drop a misspelt key without a word, and a refusal the model reads now starts with `refused: `.** A declaration written in plain JavaScript, parsed from JSON or held in a widened variable never meets the type checker, so `coverage(verdict, { checked, not_checked })` returned a ledger with `checked` only: the ground the tool did not check vanished, and the answer read as if the tool had no gap. The same happened to `absent()`'s `not_checked`, `cannot_cover` and `try_instead`, to the lists inside a `semantic()` declaration's `coverage`, and to any extra key in its `clarify`. Now every key a declaration carries is one the helper reads, or the helper refuses it and names the spelling you meant when the key differs only in case or underscores: ``refused: 'not_checked' is not a field this vocabulary has — did you mean `notChecked`? The fields are: checked, notChecked, cannotCover.`` This holds for the declaration itself and for every object `semantic()` reads inside it (`grain`, `provenance`, `coverage`, `clarify`, `render`), so `measuredAt` is refused and `measured_at` is named. A coverage item's own keys (`what`, `why`, `short`, `kind`) are unchanged, and an unknown one there is still dropped; data rows (`series`, `facts`, `edges`) still pass their columns through.

These helpers run inside a tool's `execute`, so a refusal becomes that call's error result, which is the text the model reads in place of the data. It used to start with the helper's name (`semantic: carries series/facts with no provenance…`, `absent: …`), and a line starting `absent:` can read like a finding. No provider adapter marks a tool result as an error on the wire, so the words are all the model has. Every refusal from the three helpers now starts with the same neutral prefix, `refused: `, whichever helper refused. For example: ``refused: this result carries series/facts with no `provenance` — `provenance.measured_at` and `provenance.source` are required whenever the envelope carries data…``. The four `semantic()` rule messages that had no subject now begin `this result …`, which also changes their wording in `explainSemantics` and in `check:semantics` findings. The run continues as before, and a correct declaration returns exactly the bytes it always did. If your code matches these messages, match the text after `refused: `.

**The answer account says "It ran {tool}" only when the record shows the tool ran.** A call that ended in an error before its tool was reached (a tool name that does not exist, arguments the schema rejected, a blocked credential) used to read "It ran reboot_host, and the tool reported an error." and "reboot_host returned an error, not a result.", the same words as a tool that ran and threw, and "Nothing to report: none of the tool calls ran." was said even when a tool had run and thrown. Now such a call reads "It asked to run reboot_host; the call was not executed." and "reboot_host did not run, so it found nothing."; a tool that ran and threw reads as before. "None of the tool calls ran" is said only when every call is known not to have run; otherwise the line is "Nothing to report: no tool call returned a result in this record." Answer-account template set 16 (six new sentences; no existing sentence changed).

What changes for an app:

- `stream.tool_end` carries a new field, `entered`: `false` on every bracket of a call whose tool's function was never entered (except a bracket that already says so with `notExecuted` or `notDispatched`, which keeps its bytes), `true` beside `error` on a call whose tool ran. A call that succeeded keeps exactly the bytes it had. An app that compares saved `tool_end` payloads byte for byte sees `entered` on those brackets.
- `ToolCallFact.outcome` (the account's `facts.calls`) gains `'not-executed'` (the tool never ran) and `'ended-in-error'` (an error on a record that does not say whether the tool ran). `'failed'` now means the tool ran. `facts.errors.failed` still counts every call that ended in an error. A `switch` over the outcome needs the two new cases.
- The tool-call ledger an answer check reads (`context.toolCalls`) lists a call whose tool never ran as `'not-run'`, also when it ended in an error. An unknown tool name, rejected arguments or a missing consent or credential used to be `'error'`; `'error'` now means the tool ran. A check that looked for `'error'` to catch an unknown tool name must look for `'not-run'`.
- The check-in summary an approver reads (`CheckInRequest.evidence.trail.summary`) counts calls, not runs: "3 tool calls over 2 iterations" (was "3 tools run over 2 iterations"), "no tool calls yet (iteration 1)" (was "no tools run yet (iteration 1)"). The history it is built from cannot say whether a call's tool ran.
- The trace toolpack's `inspect_tool_call` says "ran with: nothing" and "was not executed: the tool was never entered" for a call whose tool never ran, including one a rule refused.
- A recording made before this version has no `entered`, and its absence there proves nothing: an error on such a record reads "It asked to run {tool}; the call ended in an error.", never "It ran". There is no fallback that guesses from the result text.

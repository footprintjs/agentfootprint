**Where each argument value came from — the model says so, the library checks it: `.inputsLayer({ argumentSources: true })`, or `.findings({ argumentSources: true })` beside the findings ledger (the inputs layer's declared sources).** The model can say, per argument of a ruled call, where the value came from — in the reserved `_findings` argument, planted on the tools that declare `askOrAssume` only: `from: [{ argument: 'window', source: 'user', quote: 'over the last week' }]`. `.inputsLayer({ argumentSources: true })` plants `_findings` with `from` alone, so every other tool and the system prompt are served as on a plain agent; `.findings({ argumentSources: true })` (which needs the inputs layer — a tool that declares `askOrAssume`, or `.inputsLayer()`) puts `from` first, and required, in the ledger's own `_findings`; `.findings()` + `.inputsLayer({ argumentSources: true })` serves the same bytes. The sources are `user` (the person's words, copied as a `quote`), `result` (a tool_result `id`), `turn` (the person's earlier answer to the library's ask), `app` (the app's own text) and `assumed`. Before anything in the batch runs, the library CHECKS each claim against the one place that source lives, by whole-token membership (the evidence gate's own normaliser): the quote must be in the person's own messages — never a library frame, never another runner's output — and the value in the quote, or a phrase the author vouches for on that value's choice (`choices: [{ value: '7d', said: ['last week'] }]`); the value must be in the named result's own bytes (read the way the evidence index reads a result, so a number or a boolean in compact JSON is found — also behind a framework note, across an MCP text result's blocks and in a capped result's head — and the library's own note on a result never counts); an earlier answer matches the same argument of the same tool, or a period across spellings (`24h` ↔ `-24h`, `matched: 'spelling'`); `app` looks in the system messages, the composed system prompt (the library's own instructions left out) and `AgentOptions.externalGrounds` (its label rides `appSource`).

The verdict is filed on the call's `argument` row: `source` `said` (`matched: 'quote' | 'phrase'`, or `reading` when the words are the person's and the value is not in them), `answered`, `result` (`setAside` when the model had declared that result open, noise or ruled out), `app`, `default` or `model`; the claim as written (`claimed`, `quote` — `'REDACTED'` on an agent where any tool in reach can hide arguments: it registers a tool that carries an argument view (`flowchartAsTool({ redact })`, `runbookAsTool({ redact })`), or wires a ToolProvider, whatever it lists — a quote is free text that may hold any hidden value, in any spelling); a failed check (`failed`: `quote-not-found`, `composed-message`, `unknown-result`, `placed-result`, `not-in-result`, `no-earlier-turn`, `not-in-earlier-turns`, `only-in-model-answer`, `not-in-app-text`, `uncheckable`) is never repaired; a library lookup of the value is only a hint (`coincides`), never a source. A value equal to the argument's declared default that is not the person's stays `default`, whatever the claim. A free argument a `from` entry names is checked and filed with no rule; dropped `from` entries are counted on the basis row, or on the call's first argument row. The event `agentfootprint.findings.argument` carries the new enums, never a value or a quote.

What changes: under an `ask` rule, a PRESENT value the checks do not trace to a source — nothing declared, `assumed`, a failed claim, a reading — is now asked of the person in the batch's one ask (`asked: 'unverified'`; the model's value rides the row as `proposed`, never the ask); a reading's field shows the person their own words (`context.agentfootprint.fields[].quoted`); the answer replaces the value and the result's note says what the call had carried, and that a later call may cite that answer (`source: 'turn'`). The rule's served sentence says where to declare the person's words ("…leave it out unless the person gave it, and then quote their words for it in `_findings.from`."). The answer's standing gains two reasons — `argument-read` and `value-contingent` (now also read from the ledger's contingent rows of the turn; an unstamped row declared on the answer counts on a first turn, and on a later turn only where the ledger shows it is that turn's, so an earlier answer never makes this one "not sure") — and a failed claim on any argument reads `argument-unverified`; a traced value fires nothing, so checked values read "consistent with the record", never "known" (a membership pass supports nothing). `checked` gains `argument-sources`; the answer layer's standing line words the two reasons and the check. The answer account's template set moves to 7 (`howSure.reason.argumentRead`, `howSure.reason.valueContingent`, `howSure.check.argumentSources`; `howSure.reason.argumentUnverified` no longer says "ruled").

Compositions mark another runner's output: `Sequence` and `workflow()` (every step after the first), `Loop` (every iteration after the first) and `graph()` (every node that is not a root) hand a runner that reads the mark `messageFrom: 'composed'`, and `Parallel`, `Conditional` and a nested composition pass a composed message on — so another model's words never count as the person's (`failed: 'composed-message'`). New `AgentInput.messageFrom: 'person' | 'composed'` for code that composes runners by hand (any other value is refused at `run()`).

Served only under the arm: the `from` property on a RULED tool's `_findings` — explained once, in its own property; there is no instruction line — and the `ask` rule's sentence, each only on a tool whose schema carries `from`. A tool that declares `askOrAssume` AND an argument of its own named `_findings` is refused at build while the arm is on (either door; a skill's tools included), naming the tool — its sentence would tell the model to declare into the author's argument; one a ToolProvider serves runs as its author wrote it, with the unarmed sentence and note. Measured on 2026-09-28: beside the ledger the ruled tool's schema +744 characters and the system prompt +0; without it the ruled tool +863 over a plain agent's, everything else +0. Off (the default): no property, no check, no new key — every earlier run is byte-identical (the other references under `test/core/tools/reference/` did not move; `agent-arguments-sources` pins the armed run beside the ledger and `agent-arguments-sources-only` without it). The arm is opt-in, and its registered benchmarks (v1 and v2) did not pass. The checks are correct — no fake quote was verified, and cited values were traced to their results — but on Haiku 4.5 the model rarely declares a source for the person's words (in v2 it put the value in `_findings.from[].argument`), so values the person stated are asked of them again. An improvement is in progress.

Surfaces that widen, named: `ArgumentRow` rows now carry `claimed`, `matched`, `quote`, `reading`, `earlier`, `result`, `setAside`, `argumentsFrom`, `appSource`, `coincides`, `malformed`, `failed` and `asked: 'unverified'` (the fields were declared; they are now written); `AssessmentReason` gains `argument-read` and `value-contingent`, `AssessmentCheck` gains `argument-sources` (a reader that switches over every member must skip one it does not know); `FindingsDeclaration` gains `from`; `AgentState` gains `userMessageFrom`; `HonestyLayers` gains `argumentSources`; `ArgumentResolution` gains `quoted`; `AgentOptions.inputsLayer` also takes `{ argumentSources?: boolean }` (and `AgentBuilder.inputsLayer(options?)` the same), anything else refused at construction.

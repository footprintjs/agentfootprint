**`fileObservability` no longer tears NDJSON lines by overlapping its own writes.** The file sink's timer started its write directly, while size-triggered writes and `flush()` waited their turn. A large `appendFile` is several writes, so a timed append could overlap another one: lines were split and failed `JSON.parse`, events landed out of order, two batches could skip a rotation, and `flush()` could return before a timed write landed (reported in #223). `cloudwatchObservability`, `agentcoreObservability` and `xrayObservability` had the same timer, so two puts could be in flight at once and `flush()` could return early.

All three now share one queue: every trigger (size, timer, `flush()`) waits its turn, one batch is in flight at a time, and batches leave in the order events arrived. File rotation runs inside that turn. This keeps one sink's writes from interleaving; it does not make a write atomic — a disk that fails partway through an append (ENOSPC) can still leave part of a line behind, as before, and that batch is reported dropped. `flush()` resolves once every event accepted before it was called has settled — written or shipped, or dropped and reported — a timed write already in flight included, after one more sweep of what arrived while it waited. It does not chase a producer that keeps emitting. A failed batch is still dropped and reported once, and later batches go on. An `onError` hook that throws is now reported on the console instead of becoming an unhandled rejection.

The batch-size options keep the meaning they had. For `maxBufferEvents` (file) and `maxBatchEvents` (CloudWatch, AgentCore), every value works as before: `0` or a negative number still delivers every event at once, `2.5` still triggers on the third event, and `NaN` still never triggers by count. X-Ray's `maxBatchSegments` still puts its whole part at a time (`2.5` → two segments a put). The one value now refused never worked: a `maxBatchSegments` below 1 (`0`, a negative number, `NaN`, a fraction under 1) made every put take no segments, so empty puts ran in a loop. It is refused when the strategy is built, and the error names the option.

Because puts now go one at a time, a slow CloudWatch put lets a backlog build behind it. Each delivery is now split to fit CloudWatch's documented `PutLogEvents` limits — at most 10,000 events and 1,048,576 bytes per request, counting each event's UTF-8 message bytes plus 26 — and the rest ships in the next request, in order. Without the split, the backlog went out as one request CloudWatch refuses, and every event in it was dropped. An event too large for any request is still sent on its own, as before; CloudWatch refuses it, and only that event is reported dropped. A part that fails is dropped and reported on its own, and the parts around it still ship. `maxBatchEvents` and `maxBatchBytes` still decide when a delivery starts.

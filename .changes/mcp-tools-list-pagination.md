**`mcpClient` now reads every page of a server's tool list, says so when it cannot, and every tool keeps the MCP SDK's call checks whatever is listed later.** `tools()` and `refresh()` read only the first page of `tools/list`, so a server that paginates its catalogue was cut short in silence: the agent was offered part of it and nothing said so.

The client now follows `nextCursor` until a page carries none, sending at most 100 `tools/list` requests (a bound on requests, not on the catalogue's size). A list that does not end within them, or a page that names a cursor the listing already sent (a loop), is no longer returned cut short: the call rejects with the new `McpToolListIncompleteError` (`agentfootprint/providers`), whose `reason` is `'page-limit'` or `'cursor-repeated'`, whose `pages` counts the pages read and whose `tools` holds what was listed, callable, for a caller that chooses to use an incomplete list. The client's `signal` rides every page and is checked before each page is asked for and when each answer arrives: once it has fired, nothing more is asked for and no page is accepted, the last one included. A server that answers in one page gets exactly the request it got before.

Every tool keeps its checks, whatever is listed later. The SDK's `Client` checks a tool call only for the tools of its most recent `tools/list` answer, and every answer replaces those checks: a tool that requires task-based execution is refused before it is sent, a tool with an `outputSchema` must answer with `structuredContent`, and that `structuredContent` must match the schema. So every tool `mcpClient` hands out now carries these checks, as its list declared them. The SDK is left to run them only for a tool of a one-page list whose answer is still the latest, with no list request out when the call starts or ends; that usual case sees no change. Every other call runs the tool's own checks and raises the same error: a paged list's tools, a tool kept across a later `refresh()` (whether it succeeded or failed), and a call made while a list is being read. A failed `refresh()` still rejects and `tools()` keeps serving the old catalogue, whose tools stay checked. The error is the SDK's own `McpError` where the library loaded the SDK, and otherwise has the same name, `code` and message. The output checks use the SDK's default validator, loaded with the SDK, or the new `jsonSchemaValidator` option (typed `McpJsonSchemaValidator`, the SDK's own interface, so `new AjvJsonSchemaValidator()` fits as is). On the `sdk` arm, the client the library builds is handed that same validator. On the `sdk` and `connection` arms without `jsonSchemaValidator`, an answer is never returned unchecked: such a call to a tool that declares an `outputSchema` is refused with the new `McpOutputUncheckedError` (`reason: 'output-unchecked'`), before it is sent (`sent: false`) or, when a list was read while the call was out, once its answer is in, unread (`sent: true`).

`McpConnection.listTools` now takes an optional `{ cursor }` and may return `nextCursor`, and `McpListedTool` carries `outputSchema` and `execution`, as the MCP SDK's own `Client` already does: a connection that never pages is unaffected. On the Node loader arm, building a client now also loads the SDK's `types.js` and `validation/ajv` modules, which the SDK's own client module already loads.

**A check-in tells the person which argument values the tool's view hides, binds that list to the approval, and the record keeps what the person was told.** A tool can carry an argument view that hides some values (`flowchartAsTool({ redact })`, `runbookAsTool({ redact })`). A check-in on such a tool showed the person `to: 'REDACTED'` and ran with the real account on approval, but nothing said which values were hidden: a real argument whose value is the string `'REDACTED'` looked exactly like a hidden one, and the decision's record could not tell an approval given on a hidden view from one given on the whole call. The chat-interface adapter (AG-UI) also streamed the real arguments to the same page that asked for the approval.

What an app will notice:

- **`CheckInRequest.hiddenArgs`** (new): the names of the arguments the tool's view hides, absent when none. It is the library's reading of the view, never of the shown text, so a real `'REDACTED'` value is not listed. A name is listed when the view's output for it differs from the input or the library could not decide; it cannot see a view that is not a function of its input alone, nor a placeholder that is not a string equal to the real value. *To do:* show the list next to the arguments on your approval screen.
- **The built-in `evidence.willDo` gains one sentence** when values are hidden: ``Values hidden from this view: `to`. The call runs with the real values.`` Each name is quoted, because the names are the model's text. *To do:* a screen or test that compared `willDo` for such a tool expects the new ending. A custom assembler is handed the names as `CheckInAssemblerInput.hiddenArgs` and writes its own words.
- **The request id commits to the list.** The names are bound when the request is made, kept on the paused request and read back on resume, never worked out again from the tool. A check-in pause now stores `hiddenArgs` on its paused request (`[]` when nothing is hidden); the id leaves an empty list out, so a tool without a view derives the same id as before. *To do:* nothing; a checkpoint whose list was edited is refused as `'call-changed'`, like any edited call.
- **A changed view voids the approval: new refusal `'view-changed'`** (`ResumeDecisionRefusal`, `ResumeDecisionError`). If the resumed tool's view would hide a different set of names than the request carried (a redeploy widened, narrowed or removed it), the resume is refused before the decision is spent and before anything runs. The message names the difference by argument name, never by value. A host that keeps the pause (`standingAgent`, `streamHandler`) closes it, as it closes `'call-changed'`. *To do:* a host that maps refusal reasons handles one more; the person is asked again.
- **The decision's record carries the list** (`checkin.decision` · `CheckInDecisionPayload.hiddenArgs`, `CheckInRecorder` · `CheckInDecisionRecord.hiddenArgs`), as the request carried it. A pause stored before this release has no list: its decision reads `hiddenArgs: 'not-recorded'`, one fixed value meaning the record does not say what was hidden. *To do:* a reader of the field handles a string as well as a list. Under a run's redaction policy the names are masked like any string the library did not write (the tool's name is too).
- **`stream.tool_start` gains `shownArgs` and `hiddenArgs`** for a call whose tool's view hides something: the view's output and the names, beside the real `args`, which are unchanged. Every other call's event is byte-identical. *To do:* a listener that writes whole payloads somewhere now also writes the view's form; a listener that shows arguments to a person should show `shownArgs` when present.
- **The AG-UI adapter streams the view, not the values.** For such a call, `TOOL_CALL_ARGS` carries the view's output, and `TOOL_CALL_START` and a check-in's interrupt carry the names as `metadata.agentfootprint.hiddenArgs` (`AgUiAddress.hiddenArgs`). *To do:* a page that read the real values from `TOOL_CALL_ARGS` no longer receives them for such a tool.
- **The view runs on a frozen copy** of the call at the check-in, at the resume's check, for `stream.tool_start` and for the private-answer marks, and a string the view handed back unchanged is probed on its own. A view that writes into its input now throws there, and every argument is listed. The private-answer marks (`arguments/privateAnswers.ts`) use the same reading: a hidden value already equal to the placeholder is marked private, a key the view only adds is not, and a view that checks a value's type is no longer read as hiding the arguments it passes through. *To do:* nothing, unless a view of yours writes into its input; then fix the view.

What the view does not cover: the run's own events still carry the real arguments — `stream.tool_start` (its `args`) and `agent.iteration_end` (its `history`) — and so do the recorded history and snapshots, unless the app's redaction policy covers them. The answer account shows a check-in decision's `approved`, `toolName` and `toolCallId`, not its `hiddenArgs`. `execution/dispatchCall.ts` still runs the view on the call's own arguments for `stream.tool_end`'s `changedArgKeys`, so a view that writes into its input can still change the call that runs, as before. No hidden value reaches the check-in request, its sentence, the check-in events, `CheckInRecorder`, the AG-UI tool-call arguments or a `'view-changed'` refusal's message. A tool's result is not a view: what the tool returns reaches the page as it always did.

**Call MCP servers hosted on AWS Bedrock AgentCore Runtime.** `agentCoreRuntimeMcpTransport({ agentRuntimeArn, region })` (from `agentfootprint/providers`) is an ordinary MCP transport for a server deployed to AgentCore Runtime with `--protocol MCP`, so `mcpClient` lists and calls its tools like any other server. It handles the three things that make such a server different from a plain URL, each as a strategy you pick by name:

- **auth** — `'sigv4'` (default) sends every request through the AWS SDK's `InvokeAgentRuntime`, with the MCP headers on the SDK's own fields (`mcpSessionId`, `mcpProtocolVersion`, `runtimeSessionId`, `contentType`, `accept`, `payload`). `{ bearer }` is for a runtime behind an OAuth authorizer: the SDK has no bearer scheme, so the request goes to the documented HTTPS endpoint with a machine token vended per request and dropped, by the same code as `gatewayTransport` (`mode: 'user'` is refused: the request names no user). On both paths an auth failure (401, 403 or an AWS auth error type) reaches the MCP client as its type and status only — AWS can quote the signed request in the message, session token included.
- **session** — `'per-call'` (default) sends no session id of its own and hides the one the runtime returns, so nothing carries over between requests and one client can serve every user of a process (it needs a stateless server, the runtime's recommended default). `'reuse'` keeps one runtime session per client, keyed by the transport: a client's first request gets a fresh runtime session id, the server's `Mcp-Session-Id` is kept with it, and the client carries a random handle in its place (an unknown handle is answered 404 unsent; at most 256 connections, least recently used forgotten first). Build one `'reuse'` client per conversation. Every attempt of one request goes to the same runtime session, and a failure's text never repeats a session id or token the request sent.
- **retry** — the runtime's "Session operation in progress, please retry" refusal arrives as an HTTP 200 with a JSON-RPC `-32005` error (or, at the API layer, a 409 `RetryableConflictException`), which MCP clients do not retry. It is now retried with bounded, jittered backoff (5 attempts, at most 10 s of waiting by default; `retry: false` turns it off). Only that refusal is retried — not `ConflictException`, which shares the code, and never a 5xx or a dropped connection, which may be the record of a call that ran: the SDK client the transport builds has the SDK's own retry off (`maxAttempts: 1`), and a non-2xx answer is handed to the MCP client as the HTTP status it was. The loop is the same one `mcpClient` uses for HTTP 429, so the ceilings and the `onRetry` report work the same way.

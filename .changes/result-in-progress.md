**In progress is its own outcome: `coverage(value, { checked, inProgress })`.** Some vendor states mean "still running", such as a backup in progress or a replication session still synchronizing. A tool that tests "equals the success value" counts those as failures. A backup two hours into its run then reads as unprotected, and an array with no unhealthy sessions reads as "97 non-OK". A tool can now say which of its items are still running, so their outcome is not known yet. The tool decides which items are in flight, and the library never reads a state name. Items are a string or `{ what, why?, short?, count? }`. `count` says how many things one entry stands for. `short` is record-only, as on every coverage item. `kind` is refused.

`inProgress` needs `checked` beside it, even when the list is empty, so the refusal never depends on the data. An empty list is omitted from the wire. A malformed list, an unknown item key and a `count` that is not a whole number of at least 1 are refused where `coverage()` is called. The snake_case `in_progress` is refused, naming `inProgress`. `absent()` does not take the key, because an absence promises a retry returns the same. `describedResult()` does not take it yet.

The model reads `in_progress` inside `af_coverage`, before `result`, with `short` stripped and `count` served. The dispatch door appends ONE static clause after the note, so an envelope a sidecar minted gets it too: *"`in_progress` is what the call this result answers found still running: its outcome is not known yet, so it is neither a success nor a failure — report it as in progress, never as either."* The tool's own output keeps `COVERAGE_NOTE`, and the evidence corpus never counts the clause. This is new model-facing text, served only when a tool declares a non-empty list. It is registered as a model-facing surface, and no benchmark has measured it yet. A foreign `in_progress` is read by the same rules, and extra item keys ride through. A malformed foreign list is left off the record, with one dev warning per tool, and served as written.

The record: `agentfootprint.tools.coverage_declared` and the `coverageDeclared` row gain `inProgress`. Under `.limitsTravelWithTheAnswer()`, a prose answer gains an `In progress (outcome not known yet):` section with one line per item and the tool name first. A typed answer gains `answerCoverage.inProgress`, with one entry per declaring call (`{ toolName, toolCallId?, items }`). The answer's standing does not change: the declaration is a label, not a reason. Deciding "not sure" only when an answer called an in-flight item settled would mean reading the answer's words. `canonical-notes.json` publishes `IN_PROGRESS_WIRE` (`{ key: 'in_progress', count: 'count' }`).

New exports: `IN_PROGRESS_WIRE`, `IN_PROGRESS_CLAUSE`, `IN_PROGRESS_SECTION_LABEL`, and the types `InProgressItem`, `InProgressInput` and `AnswerInProgress`. Surfaces that widen: `CoverageLedgerDeclaration.inProgress`, `CoveredResult.af_coverage.in_progress`, `DeclaredCoverage.inProgress`, `ToolCoverageDeclaredPayload.inProgress` and `AnswerCoverage.inProgress`. `in_progress` is now a reserved list on a recognized envelope: its items' `short` and `kind` are stripped from what the model is served. A tool that declares nothing is served, recorded and answered byte for byte as before. Example: `examples/features/79-result-in-progress.ts`.

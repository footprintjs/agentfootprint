**A tool called from inside another tool passes the same gates as a call the model makes, and leaves its own row.** `ctx.tools.call(name, args)` now puts the inner call to the agent's `permissionChecker` (its `tool_call` question, the capabilities the tool declares that the checker governs, and `skill_read` for `read_skill`) and to its before-tool middleware links, through the same functions and in the same order as a model call, with the inner call's own arguments and under its own id (`<outer call id>#inner-<n>`). A sequence rule sees the inner calls, and a checker's `'halt'` on one ends the run. Before, an inner call was asked nothing: a tool the checker or a middleware refused to the model ran when another tool called it.

What "governs" now means: your `permissionChecker` and `.toolMiddleware()` links decide every `tool.execute()` the agent's dispatch makes — the model's calls, and the calls a tool makes through `ctx.tools`. A checker is now asked about calls the model never proposed (`actor` is still `'agent'`; the id ends in `#inner-<n>`).

What an app will notice:
- **A composed tool that calls a tool your checker or middleware refuses now gets an `Error`** from `ctx.tools.call` naming the tool and the refusal, and the inner tool does not run. A middleware `ask` refuses the inner call too (a person cannot be asked from inside another tool). To do: let the composing tool handle the error, or allow the inner call in your rule.
- **A checker's `'halt'` on an inner call ends the run.** The inner call is refused at once (the composing tool reads the halt's `tellLLM`, never its `reason`); once the outer call settles and its result lands, `permission.halt` fires under the inner call's id with the inner tool as `target`, later calls of that turn do not run, and `agent.run()` throws `PolicyHaltError` whose `proposed` is the inner call. To do: catch `PolicyHaltError` as you do for a model call's halt; an alert route that keys on the event's `toolCallId` sees `#inner-` ids.
- **The `sequence` a checker is handed includes inner calls.** Each inner call whose tool ran follows its outer call, marked `inner: true` (new optional field `ToolCallEntry.inner`), with its arguments shown through the tool's argument view; an inner call's own checker also sees the earlier inner calls of the same outer call. A rule such as "no post after a secret was read" now refuses the chain when a composing tool takes either step. To do: a rule that must count only the model's own calls filters out entries with `inner: true`.
- **The outer call's history message carries the inner calls that ran** (new optional field `LLMMessage.calls`), so a later turn — and anything else that carries the history whole — keeps them for the sequence. It is removed before any request reaches a provider. To do: nothing, unless you compare stored history bytes or build requests from history yourself (then drop `calls` as the library does in `stripFrameworkFields`). If your hand-written redaction list does not name `history`, inner arguments now also appear there.
- **An inner call runs on its own copy of the arguments,** taken when `ctx.tools.call` is made; a composing tool that changes its object afterwards no longer changes what the checker judged or what runs, and the inner tool is handed the copy, not the composer's object. Arguments that are not an object (a string, an array, `null`) are refused with the schema check's own sentence whether or not a gate is configured; arguments `structuredClone` cannot copy (a function inside) are refused by name; no arguments at all now run as `{}` (the tool used to receive `undefined`). To do: pass plain data.
- **Refusals come in the model call's order:** the permission check, the tool's argument rules, the middleware chain, an unknown name, the schema, the `skill_read` question, then the check-in and `wants` refusals. An inner call to a `checkIn` or `wants` tool is now walked through the middleware before it is refused, and an unknown name is put to the checker and the middleware first, as a model call's is. To do: a checker or link that assumes the named tool exists must handle an unknown name, as it already must for the model's calls.
- **A `ctx.tools` kept past its outer call's `execute` is refused** by name; its row says `refusedBy: 'ended'` while the outer call's stage is still open. To do: make inner calls inside `execute` and await them.
- **More events and rows under inner ids.** Each gated inner call files its own `permission.check` and `middleware.decision` events and `middlewareDecisions` rows under `<outer>#inner-<n>`; no `tool_start` / `tool_end` fires for it, so the library's readers of the model's calls count as before. To do: app code that counts those events or rows as calls the model made should skip ids containing `#inner-`.
- **A new state key, `innerToolCalls`:** one row per inner call (`toolCallId`, `outerToolCallId`, `toolName`, `iteration`, `args` through the tool's argument view, `entered`, `ended`, `refusedBy`, `halted`), with or without a gate. `conversationRedaction()` keeps the key out whole (its vocabulary version changes). To do: if you list redacted state keys yourself, add `innerToolCalls`.
- **The inner id after a refused inner call is one higher than before:** every `ctx.tools.call` takes its id when it is made, a refused one included.
- **The answer account** (`accountForAnswer`) no longer reads a `permission.check` filed under another call's id as a verdict on the call it is reading. It does not name inner calls.

Not changed here: a checker answer the library does not recognise (`{ result: 'ALLOW' }`, `{}`) still allows the model's call and the inner call alike on this release's base; the rule "only a known allow allows" arrives with its own change and reaches inner calls with no further edit. A middleware outcome the chain does not know (`{ kind: 'maybe' }`) still allows, for both.

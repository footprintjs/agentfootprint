**An approved call runs with the arguments the person approved, and a closed pause says "did not run" only when that is proven.** Two follow-ups to binding decisions to their request.

**Arguments after an approval.** A tool's `checkIn` predicate, asked again when an approved middleware `ask` resumed, was handed the very object the tool then ran with: a person approved a refund of 5, the predicate wrote 9000 into its argument, and the refund ran for 9000. The loop's own check-in gate had the same hole from the other side — a predicate that answered "no check-in needed" for 5 could write 9000 and the call ran unasked. Now every app callback that sees a call's arguments before it runs gets its own frozen copy, never the arguments the tool runs with: a `checkIn` predicate (at every door), a custom evidence assembler (`.checkIn({ evidence })`) and the request it builds, and a permission checker's `context`. A write to the copy throws in strict code — a predicate that throws trips the gate, so the person is asked; a permission checker that throws denies — or is ignored in sloppy code, and either way the call runs as judged. Arguments no copy can be made of trip the gate (fail toward asking) and are denied by the permission gate. As defence in depth, an approved check-in or ask call is held to its request once more at the last moment before `execute`, by the same rule that binds a decision to its call: arguments that changed after the approval do not run, the model reads why, and an ask's record keeps a `call-changed` refusal. Middleware links are the one exception by contract — they rewrite by what they hand back, and after an ask what they hand back is already held to the request. `outcome.checkIn` itself is unchanged: the served copy is not frozen.

**"Did not run" only on proof.** A hosted door (`standingAgent`, `streamHandler`) closes a pause no answer can reach any more — and used to record every call it left open as "That call did not run". That was false after this sequence: the person approves, the refund runs (the decision is spent), the next model call fails, marking the stored pause answered also fails (a store error), and a redeploy changes the middleware rules so no answer can reach the pause; the next message told the model the refund never ran — and a model told that may issue it again. Now a closed pause's calls are recorded as not run only when the serving agent's ledger proves no decision for the request was ever spent: a shared `decisionLedger` whose `isSpent` answers `false`, or this process's default ledger for a request this process minted. Otherwise — a pause stored before the process started, an app's own `inMemoryDecisionLedger()`, a runner whose ledger the host cannot see (a composition), a ledger without `isSpent` or one that throws, a pause from an earlier release that names no request — the model reads "That call's outcome is not known: its approval may have been used, and whether the call finished could not be confirmed." (`toolResultOrigin: 'outcome-unknown'` under findings admission, which the findings reader treats as unknown rather than not dispatched). A call the record proves never ran — declined, or refused before dispatch — still says so. Session listings are unchanged: they say whether a pause waits, never whether its call ran.

No public API changed. Runs neither bug touches behave as before; the visible differences are a predicate, assembler or permission checker that wrote into its arguments (now refused by the copy instead of changing the call), and a closed pause whose non-execution cannot be proven (now "not known" instead of "did not run").

# Hosting, identity and security — seams and blast radius

Loaded only when you work on the paths above — moved verbatim out of the root CLAUDE.md so it costs context only where it applies. **Trust the code** where this disagrees.

## Extension points
- **Identity verifier (9.26.0)**: `IdentityVerifier` = `{ verify(token) → VerifiedIdentity }` (hosting/identityVerification.ts) wired at `standingAgent({ identity: { verify, allowAnonymous? } })`. Runs ONCE at the top of the handler, BEFORE `identityForRequest` composes scope, and its answer is shared by all three doors (turn / artifact / session-op) — a later door cannot be the lenient one. Extraction is `bearerToken(headers)` (the ONE reader; every dialect normalizes onto `authorization: Bearer`). Refusals carry `IdentityFailureClass` and NEVER the token (`sdkFailure` law); a key set that could not be FETCHED is `VerifierUnavailableError`/503, not 401. One adapter: `jwksIdentity` (adapters/identity/jwks.ts) over `jose` (optional peer, ESM-only ⇒ dynamic-import-then-lazyRequire, structural `JoseBackend` seam), mapping by `err.code` STRING not `instanceof` (the classes are not on jose's main entry; codes are pinned by test/adapters/identity/jwks.test.ts against the real package).
- **Identity strategies (unreleased)**: `identityFromConfig(config, { production })` (adapters/identity/strategies/choose.ts) is the ONE judge of a deployment's `IDENTITY_*` settings — ASYNC because a discovery config error must refuse the BOOT. `vocabulary.ts` is the one list of strategy names and keys, including keys a later release reads (`KEYS_IN_A_LATER_RELEASE` — refused by name, never ignored); a new strategy moves its keys from that map to `KEYS_IN_THIS_RELEASE` and its name into `STRATEGIES_IN_THIS_RELEASE`. `oidcIdentity` (adapters/identity/oidc.ts) = discovery cell (single-flight; `ready`/`misconfigured` final, `outage` retried after `discoveryRetryMs`) → `verify/jwtCore.ts · verifySignedToken` (the ONE signature/iss/aud/exp/nbf check, shared with `jwksIdentity`; `exp` required twice — `requiredClaims` AND a post-check, so a stub backend cannot skip it) → `verify/personTest.ts · personTestFailure` BEFORE the id claim is read (so an app token is named `not-a-user-token`, not `unverifiable`) → overage (`rolesAreElsewhere`) → roles as a LIST. Every strategy runs `test/adapters/identity/conformance/cases.ts · identityStrategyConformance`; a strategy that cannot satisfy a law DECLARES it (jwksIdentity declares the person-test cases), and a declared case that passes is stale. Browser sign-in, `proxy-token`, the password strategies and the door-hardening boot coupling (H1/H4) are later packets; H1 does not apply to token-only `oidc-token` (a bearer header is not ambient).
- **Credential seam (unreleased)**: `hosting/signin/`. The host option `signIn: { cookieName?, identity }` (checked at construction by `signin/hostSignIn.ts · checkHostSignIn`) makes `httpHost · dispatchOne` and `conversationDoor · handleUpgrade` read headers through `signin/cookie.ts · readSignIn` INSTEAD of `lowerCasedHeaders` — the cookie is gone before any dialect (`readRequest`/`readConversation`) or handler reads a header, and `signInKey` is spread conditionally (no key ⇒ no property: the zero-delta pin in test/hosting/credential-seam.test.ts checks `Object.keys(request)`). `verifyRequestIdentity` takes the key as a 4th arg: two credentials → `'two-credentials'` FIRST, then a key with `options.signIn` → `signedIn` (store fault → 503), else the old token path verbatim (via `presentedToken`, which is `bearerToken` unless `tokenHeader` names another header). The conversation door: no `signIn` ⇒ `admit()` runs synchronously exactly as before; with it the handshake is verified async (`checkHandshake`) and only then the 101; a socket admitted by a KEY gets `watch` — every frame waits on a promise chain (`gate`) for `signInStillLive`, `onEnd` closes it 1008. Lifetimes live ONLY in `signin/source.ts · signInSource` — a store never judges expiry.
- **Sign-in door (unreleased)**: `hosting/signin/door.ts · signInDoor` — a `(req,res) → handled?` app handler (mounted on `onUnhandled`), NOT a host door; it builds its own `doorGuard` from the host's lists (`guard`, H4: the public URL must pass them; unset only for a loopback public URL, H1) and calls `guard.check` on EVERY `/auth` request. Login order is load-bearing: guard → own capped body reader (fixed sentences; never the JSON parser's text) → `attemptLimiter.before` (+ delay) → end a present sign-in → `PasswordChecker.check` (throw ⇒ 503) → create; every login answer waits for `minimumResponseMs`. Lifetimes stay in `signInSource`; the door owns `signIns` and exposes `identity`/`hostSignIn` so the host and `standingAgent` get the SAME source (and `onEnd` closes sockets on logout). `local-password` = `adapters/identity/localPassword.ts` (scrypt, hash-only, decoy check for unknown names) + `strategies/localChoice.ts` (refused in production). Keys carry an `owner` strategy in `vocabulary.ts`; `choose.ts · refuseForeignFields` refuses another strategy's key.
- **Redirect sign-in (unreleased, PENDING INDEPENDENT REVIEW)**: `signin/redirectRoutes.ts` (the door's redirect half) + `adapters/identity/oidcSignIn.ts` (the protocol, over `openid-client`, optional peer, `OpenIdClientBackend` slice). The Configuration is built from OUR checked discovery document (`DiscoveredIssuer` now carries the endpoints, each `fetchableUrlProblem`-checked) — never `openid-client`'s own discovery, so the no-redirect / https rules hold. The transaction is sealed (`seal.ts`, AES-GCM, AAD = cookie name) into `<cookie>-tx-<attempt>`; `state` = `<attempt>.<random>` names the cookie. `readSignIn` strips tx cookies too. The person comes from the ACCESS token via the strategy's `verify` (never the ID token). Failures redirect with a `RedirectFailure` code only. `browserChoice.ts` turns it on from config (all-or-none) and refuses audience == client id. idI57: `RedirectSignIn.ready()` is AWAITED at boot (`browserDoor` is async) — missing `openid-client`, a non-RSA/P-256 key, discovery without auth/token endpoints, or PKCE required without `S256` refuse the boot; a discovery OUTAGE does not. `redirectRoutes` logs a failure CLASS once per change (`note`/`recovered`), expires tx cookies beyond the newest `KEPT_PENDING` (2) on each login, re-seals with `returnTo='/'` past `MAX_SEALED_BYTES`; `safeReturnTo` caps the KEPT form at 512 bytes and maps anything under the door prefix to `/`. The RFC 9207 flag and `code_challenge_methods_supported` ride `DiscoveredIssuer`.
- **directory-password (unreleased)**: `adapters/identity/directory/` — `port.ts` (the `Directory` port, `escapeFilterValue`, `sidToBytes`), `directoryPasswords.ts` (the rules: empty password → name check → bind `<name>@<domain>` → Who-am-I → `accountFilter` → EXACTLY one entry → objectGUID base64 → nested group at base scope), `ldapDirectory.ts` (ldapts, LDAPS only, Node's own host-name check). The typed name is NEVER used to find the person (the rename collision). Limits (idI57): `strategies/directoryChoice.ts` sets `perName = floor(threshold/3)` (a third: an account can have TWO logon names — UPN prefix and sAM — that no service-account-free door can tie together) over AD's window on the SAME limiter the password door uses (counted at start — idI34 B-1), keyed on `PasswordChecker.budgetKey` (the ACCOUNT: lower-case, `DOMAIN\` and `@suffix` stripped, NFC — never the typed spelling), and the counter resets a full window after the LAST attempt (`limits.ts` `lastAt`, AD's rule). Threshold 1–2 refuses to boot unless `IDENTITY_LDAP_ACCEPT_LOW_THRESHOLD=yes`. Only `PasswordCheckUnreachableError` (no TLS connection ever opened — `ldapDirectory` watches `secureConnect` through `createSecureConnection`) un-counts an attempt; any other throw stays counted. PENDING INDEPENDENT REVIEW. The fake directory (`test/adapters/identity/conformance/fakeDirectory.ts`) applies explicit-UPN-before-implicit precedence; keep it that way or the collision test proves nothing.
- **proxy-token (unreleased)**: `strategies/proxyChoice.ts` = `oidcOptions(…, { strategy: 'proxy-token', literalIssuer: true })` + `discovery: 'off'` + `jwksUrl` + `tokenHeader` on the identity. The door guard check is the SAME function the sign-in door uses (`signin/browserGuard.ts · browserDoorGuard`, `insecureCookie: false` — proxy-token sets no cookie). Only `access-token` is accepted. The JWKS fetch is jose's (`redirect: 'manual'`, pinned by a test).
- **Admission policy (9.26.0)**: `AdmissionPolicy` = `{ decide(ctx) → 'allow' | {queue:true} | {refuse} }` (hosting/admission.ts) at `standingAgent({ admission })`, consulted once per turn BEFORE lane selection. Fed by `spendLedger()` — an in-process rolling window keyed by `spendKeyFor(identity)`, filled from `stream.llm_end` (tokens) + `cost.tick` (usd, ABSENT when no pricing table). Turns counted at ADMISSION, not completion. `{queue:true}` threads `queueAnyway` into `serialize` (bypasses the `'reject'` collision check only). Built-in: `turnsPerHour`. Absent ⇒ no ledger, no listeners, zero delta.
- **Session-history ops (9.26.0)**: a SECOND domain on the wire's `op` field. `hosting/wireOps.ts` is the ONE list (`WIRE_OPS`/`isWireOp`/`refuseUnknownWireOp`); each domain reader DECLINES the other's ops and both raise the same unknown-op refusal, so ordering between `readArtifactWireOp` and `readSessionWireOp` is not load-bearing. `SessionLifecycle` gained OPTIONAL `listByUser?`/`ownerOf?` (feature-detected; absent ⇒ `SessionIndexUnavailableError`, never an empty list). Ownership is DERIVED by `envelopeOwner(envelope)` at persist time — `persist` takes no owner — and WRITE-ONCE in both stores (memory: `!owners.has(id)`; sqlite: `owner = COALESCE(<table>.owner, excluded.owner)` — reversing that argument order transfers sessions by writing). Cross-user transcript = `SessionNotFoundError`, identical to missing. Both ops REQUIRE `identity` configured. **The ORDINARY TURN door asks the same question** (`mayOpenSession` in standingAgent, right after `hydrate` and before the strict readers, covering the `decision`/resume path too): with a verifier configured, `envelopeOwner(stored) === verified?.userId` or the same `SessionNotFoundError` — anything less made the transcript 404 decoration in front of a door that hydrated the same conversation into a model AND re-stamped its owner. No verifier ⇒ the check does not run (zero delta). Consequences stated in the option doc: pre-verification sessions name no owner and cannot be continued at a verifying door, and a refused turn does reveal that an id is taken. sqliteSessions added `owner`/`message_count` columns + an index WITHOUT a schema bump (older readers name their four columns explicitly; `SESSIONS_COLUMNS` stays the original four so a 9.25 file still opens, migrated by ALTER TABLE).
- **Ingress record (9.32.0)**: `standingAgent({ onIngressDecision })` — ONE record per DOOR decision, filed when the reply reaches its terminal. The funnel is ONE place: `handler` wraps the host's reply once (`beginIngress`/`IngressNote.watch`, hosting/ingressRecord.ts) and `answerRequest` is the old body verbatim, so no exit path reports and none added later can forget. Optional terminals are spread CONDITIONALLY on the wrapper (`awaiting`/`artifact`/`sessions`) — defining one the host lacks would tell the composer it can describe a pause it cannot and kill the `PauseNotCarriedError` path. The record carries classes + identifiers only: no token, no header, no claim set, **no error message** (only `code`/`name` — the `sdkFailure` law). `userId` is the PROVEN id, never a claimed one. It covers what a consumer's own `verify`/`decide` cannot see (missing bearer, `VerifierUnavailableError`, cross-owner 404) and deliberately NOT a body the transport refused first (`InvalidWireOpError` is raised inside `httpHost`'s `readRequest`, before the handler exists — stated on the type, never implied). **It is a STREAM, not `auditExport()`'s chain**, and saying otherwise would make it the failure it closes. Zero-cost unset: no wrapper object, the host's own reply.
- **Door guard (unreleased)**: `httpHost` asks `doorGuard(...).check(req)` (hosting/doorGuard.ts — the ONE owner of the rules) on its request door (POST `invokePath`, on the headers alone; a refused body is never parsed, drained only when ≤1 MiB within 2 s so the sender reads the 415 instead of an RST — `refuseAtRequestDoor`/`drainThenAnswer` — then `connection: close`; on a host-owned socket `checkContinue` judges BEFORE any `100 Continue`) and in `conversationDoor` · `handleUpgrade` (before the 101): Host (421; `allowedHosts` or, unset on a LOOPBACK bind, the loopback names — decided INSIDE `doorGuard` from `DoorGuardOptions.bindHost` via `loopbackAllowedHosts`/`isLoopbackBind` (IPv6 canonicalised by the URL parser, so `0:0:0:0:0:0:0:1` counts), so the 421 can say the list was defaulted (`HostNotAllowedError.rule: 'loopback-default'`) and name the same-box-proxy fix; never `X-Forwarded-Host`; every method) → browser `Origin` (host + EFFECTIVE port, a portless Host read under `X-Forwarded-Proto` when present) / `Sec-Fetch-Site: cross-site` / an upgrade with `Sec-Fetch-Site` but no Origin (403) → `content-type` essence exactly `application/json` (415, never `+json` — Fetch §3.3.7). Health GET and the HEAD probe are NEVER asked. `checkSessionId` (1–400 chars of VISIBLE ASCII 0x21–0x7E, so a latin1 header and a UTF-8 body cannot spell one id two ways; `""` refused) runs once in `dispatchOne` after `readRequest` (every wire's body/header/cookie + the session op's own id) and after `readConversation`; `nodeHost` defaults `maxBodyBytes` to 1 MiB (`DEFAULT_NODE_MAX_BODY_BYTES`) so it never runs after an unbounded read. Refusals reach listeners of the optional port member `AgentHost.onRefusal`; `standingAgent` subscribes only when `onIngressDecision` is set → `recordHostRefusal` (door `'request'`/`'conversation'`, outcome `'cross-site-refused'` or `'refused'`). The hosted-runtime adapters spread `platformFrontedDoor(options, bindHost)` = browser rules OFF unless set on a NON-loopback bind (a loopback bind gets every plain default), and `warnBrowserRulesOff` says so once at boot; session bound stays on. `allowedHosts` unset on a non-loopback bind ⇒ `warnAllowedHostsUnset` once per host NAME per process at boot (staged default, never a boot refusal). `onUnhandled` routes are NOT guarded (that option's law) — apps call the exported `doorGuard`. `mcpServe`'s HTTP listener (`connectHttp`) asks the same guard with ALL three rules (the library owns the JSON rule — the MCP SDK is an unpinned peer whose older versions substring-matched) and the same loopback default, answering in the SDK's JSON-RPC error shape; options `allowedOrigins`/`allowedHosts` on `McpHttpServeTransport`. Design: docs/design/2026-09-door-hardening.md.

## Change-impact map
- **Permission capability vocabulary** (9.11.0) → `PermissionCapability` = `ToolCapability | 'tool_call' | 'skill_read'`, defined ONCE in adapters/types.ts and imported by events/payloads.ts (`PermissionCheckPayload.capability`) — the two used to be independent copies of the same union. The law is **enforce-when-both-sides-speak**: `Tool.capabilities` (declared, NEVER inferred) × `PermissionChecker.governs` (optional, feature-detected, ABSENCE = NO, `checkerGoverns()` is the one reader). `PermissionPolicy` DERIVES `governs` from its rules bag so "unconfigured" and "never asked" cannot drift. FOUR request sites now: toolCalls' 3 `tool_call` checks + `askCapability` (declared caps + `skill_read`). Memory-pipeline stages still build NO PermissionRequest — say so rather than imply it.

# App Use — the thinking stage as UI interactions (HLD, research first, not built)

**Status:** high-level design, 2026-09-18. Owner's ruling: research the connector, then build.
Deep design at build time.

## The idea

While the loop runs, the model makes four or five tool calls. Today the front end renders
them as status text. Instead each call becomes a **visible interaction on the product's own
screen** — the app opens the port inventory, then the counters, then the SFP diagnostics —
and the person can **block one mid-loop**. The model uses the app through its declared
tools; the app shows each use and lets the person govern it.

Not Computer Use (the model drives *any* screen through pixels and guessed clicks). The
inverse: the **app** drives its own screen from the model's *declared* calls. No pixels, no
guessing, every interaction typed and on the record.

Generative UI (Vercel AI SDK), MCP-UI / Apps SDK, A2UI render the *answer*. This renders the
*loop*.

## Where it sits in the family

| channel | state | owner |
|---|---|---|
| input — the person's interactions, declared, with their boundary | done | hcifootprint |
| output — the reply, artifacts, charts | done | agentfootprint + vizfootprint |
| **thinking — the loop's tool ask / return, live, actionable** | **missing** | the connector this page is about |

The connector is a third channel, not a new library: agentfootprint's live events (ask /
return per tool, `toolCallId` since 9.111.0) → hcifootprint's interaction model, where an
interaction may originate from the **agent** (`source: 'agent'`: "opening port inventory")
as well as from the **person** (`source: 'person'`: "block this") — and the person's answer
goes back into the loop as a recorded interrupt. vizfootprint renders whatever a tool
declares it presents.

## Laws

1. **A tool declares its interaction** — `defineTool({ …, presents: … })`. The front end
   maps the declaration to a component; it never infers from a tool name. No `presents` =
   text, as today.
2. **A block is a declared interrupt, not a kill.** The loop pauses at the ask (before the
   tool runs — `interrupt()` + checkpoint exist); the model receives the person's refusal as
   the tool's result ("the person declined this call"); the loop continues with that fact on
   the record.
3. **One record, two tellings.** Every interaction shown live is a row, so the Story Lens
   replays the same sequence the person saw. Nothing is shown live that the record cannot
   replay.
4. **Zero cost when nothing declares** `presents`: the stream and the screen are what they
   are today.

## Open questions (the research packet)

1. **Contract** — the shape of `presents` (kind: table / chart / highlight / panel; which
   fields of the args and result it binds), and whether the existing status stream is the
   wire or a typed event channel beside it.
2. **Tool results are data refs.** A tool result that is large travels as an artifact ref
   (`art_…`), not inline. For the live interaction, does the FE (a) receive the ref and fetch
   it (one more round trip, but the same door `artifact-get` the lenses use, and the record
   stays one), or (b) receive the data inline in the live event (faster paint, but a second
   copy on the wire and a second shape to keep honest)? Leaning (a): the ref is the record's
   own name for the data; the FE fetches on the ask's return, the same as the Data tab does.
   Measure the paint latency before deciding; a small inline *preview* (row count, first
   rows) beside the ref is the likely middle.
3. **Blocking semantics** — how long the loop waits; the default when nobody answers
   (proceed / decline, declared per tool or per app); what the record writes for a block, a
   timeout, an allow.
4. **Batches** — two tools in one turn are two interactions at once; which the person may
   block independently; ordering on screen.
5. **Prior art to read** — MCP-UI / A2UI (declared-component shape), browser-use (the
   live-watch UX), the Claude tool-runner per-turn approval hooks (approve/deny without a
   screen — the same gate, no picture).

## Not in scope

Pixel-level control of the screen; the FE inferring an action from a tool name or a result's
text; showing anything the record does not hold.

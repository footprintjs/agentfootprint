> A loan officer agent decides on Monday to reject application #42 — credit score 580, threshold 600. On Friday a different user asks *"why was application #42 rejected?"* You want the agent to answer from the EXACT decision evidence, not from "memory of memory" reconstruction. **That requires the framework to record the agent's reasoning at the moment it happened**, not summarize after the fact. This page shows exactly what that recording looks like.

## The fourth workflow — agent reads its own trace

If contextual errors are the new class of bug ([Why agentfootprint?](doc:why#the-new-class-of-bug)), then the trace is the recording that makes them debuggable. agentfootprint's observability hands the trace back as three workflows — Live, Offline, Detailed.

Causal memory adds the fourth: **the agent itself reads the trace.** Six months later, *"why did you reject loan #42?"* answers from the recorded evidence (`creditScore=580`, `threshold=600`), not a rerun. The trace becomes the agent's working memory.

Causal memory remembers what was *decided*, not only what was *said*.

## What gets persisted

When you configure `defineMemory({ type: MEMORY_TYPES.CAUSAL, ... })`, the causal writer stores a `SnapshotEntry` (`schemaVersion: 2`) to the configured store. It holds the `(query, finalContent)` pair and the evidence observed during **one component execution leg** of that run: the `decisions` recorded from `decide()`/`select()`, the `toolCalls` trajectory, how many iterations were observed to start, how long the observation window lasted, and the observed token usage. The type has an optional `narrative` field, but the writer does not fill it.

The snapshot is recorded evidence with its limits written into it, not a complete account of the run. When a later turn loads it back into context, every projection opens with the same boundary: the past answer may use earlier history, the evidence shows only this component execution leg, evidence from prior legs and missing observations is unknown, and empty lists do not prove that nothing happened. `availability` says how complete the evidence is:

- `observed` — the observer ran for the whole leg and no limit was reached.
- `partial` — some evidence is missing, and `causes` names why: `observer-failed`, `bounded-observation` (a limit was reached — at most 256 decisions and 256 tool calls are kept, and what was dropped is counted in `omittedObservations`), `incomplete-tool-pairs`, `duplicate-tool-start`, `missing-usage`.
- `unavailable` — no evidence, and `reason` says why (`not-configured`, `observer-failed`, `collector-failed`). The writer stores the schema version, query, final content, availability and reason. This form has no decision or tool-call lists.

### Each snapshot answers four typed questions

The snapshot maps onto the four backtrack questions every agentfootprint LLM call answers (see [Why § the four backtrack questions](doc:why#the-four-backtrack-questions)), within the one leg it covers:

| Question | Where in the snapshot |
|---|---|
| **What** happened? | `finalContent` — the answer the agent produced for the `query` |
| **Who/why** decided it? | `decisions[]` — each `DecisionRecord`: the `stageId` and the `chosen` branch, plus the `rule` label and the `evidence` values when the decision recorded them |
| **What** did it call? | `toolCalls[]` — each `ToolCallRecord`: tool `name`, `args`, truncated `resultPreview`, `errored` flag |
| **How long / how much?** | `observedIterationStarts`, `duration.observationWindowMs` (or `duration.kind: 'unavailable'`), `tokenUsage` (observed input/output only, not the provider bill) |

An `observed` or `partial` snapshot carries all of these; an `unavailable` one carries only the first row. Reading the snapshot back asks these questions of the recorded leg without re-running the agent.

## The shape (annotated)

An `observed` `SnapshotEntry` looks like this when serialized (`decisions` shortened: a real `Agent` run also records its context-slot selection):

```json
{
  "schemaVersion": 2,
  "query": "Should we approve loan #42? Credit: 580. Income: 95k. Amount: 50k.",
  "finalContent": "Application #42: REJECTED. Credit (580) below floor (600). Suggest manual review.",
  "availability": "observed",

  "coverage": {
    "scope": "component-execution-leg",
    "runId": "1794552320130-0000000001",
    "entry": { "kind": "run" },
    "priorLegs": "not-carried",
    "source": {
      "kind": "stage",
      "runId": "1794552320130-0000000001",
      "startedAtMs": 1794552320129,
      "runtimeStageId": "final/sf-memory-write-causal#46",
      "parentRuntimeStageId": "final/prepare-final#45"
    }
  },

  "decisions": [
    { "stageId": "sf-route", "chosen": "ToolCalls" },
    { "stageId": "sf-route", "chosen": "Final" }
  ],

  "toolCalls": [
    {
      "name": "lookupCreditBureau",
      "args": { "applicationId": "42" },
      "resultPreview": "{ \"score\": 580, \"bureau\": \"experian\" }",
      "errored": false
    }
  ],

  "observedIterationStarts": 2,
  "lastObservedIteration": 2,
  "toolAccounting": { "unmatchedStarts": 0, "unmatchedEnds": 0, "duplicateStarts": 0 },
  "usageAccounting": { "observedCalls": 2, "missingUsage": 0 },
  "omittedObservations": { "decisions": 0, "toolCalls": 0, "pendingStarts": 0 },
  "duration": { "kind": "measured", "observationWindowMs": 1840 },
  "tokenUsage": { "input": 1200, "output": 180 }
}
```

A `partial` snapshot has the same fields plus `"causes": [...]`. An `unavailable` one is just `{ "schemaVersion": 2, "query": "…", "finalContent": "…", "availability": "unavailable", "reason": "collector-failed" }`. A stored row of any other shape (an older snapshot without `schemaVersion: 2`, or one with a field the schema does not list) is skipped on read.

The store wraps this value in a `MemoryEntry<SnapshotEntry>` that carries retrieval metadata (`id`, `embedding`, `embeddingModel`, `createdAt`, `ttl`, …) — the query embedding lives on the wrapper's `embedding` field, not on the snapshot itself.

Three fields are load-bearing:
1. **`decisions`** — the `decide()`/`select()` choices observed in the leg: the `stageId`, the `chosen` branch, and the `rule` label and `evidence` values when the decision recorded them
2. **`finalContent`** — the agent's answer, paired with `query` for retrieval and for SFT/DPO export
3. **`toolCalls`** — the tool-use trajectory, each with `name` / `args` / truncated `resultPreview`

Together they are the evidence recorded for one component execution leg — what was observed, not the agent's whole reasoning. Prior legs are not carried, the evidence may be partial (`availability` and `causes` say so), and empty lists do not prove nothing happened.

## The four projection modes

When a snapshot is RETRIEVED for a follow-up turn, you don't always want the whole thing — context budget matters. `projection` controls what slice gets injected into the next prompt. Every projection starts with the same three lines: a header with the past query and its match score, the leg-only limit sentence, and the availability status (`Observed evidence in this leg only.`, `Partial evidence: <causes>.` or `Evidence unavailable: <reason>.`).

| Projection | What follows the three lines | Use when |
|---|---|---|
| `SNAPSHOT_PROJECTIONS.DECISIONS` (default) | each recorded decision as `stageId → "chosen"` (with `rule` and `evidence` when present), then `Tool evidence:` lines `name(args) → resultPreview` (`[ERROR]` when the call failed), then `Final answer: …` | "Why did the agent decide X?" follow-ups (smallest projection that carries the evidence) |
| `SNAPSHOT_PROJECTIONS.COMMITS` | `(no commit log captured)` and `Final answer: …` — no commit log is captured today | — |
| `SNAPSHOT_PROJECTIONS.NARRATIVE` | the stored `narrative`; the writer never fills it, so today this is `(no narrative captured)` and `Final answer: …` | — |
| `SNAPSHOT_PROJECTIONS.FULL` | the whole serialized snapshot (largest, most expensive) | Forensic-grade audit |

The default, `DECISIONS`, is the only projection besides `FULL` that carries the recorded decisions and tool evidence.

> **Note:** a footprintjs `commitLog` is not captured in `SnapshotEntry` and the writer does not fill `narrative`, so `COMMITS` and `NARRATIVE` serve only the final answer behind the same three lines.

`topK: 1` retrieves the single best-matching past run. `threshold: 0.5` is strict — if no past run cosine-matches above 0.5, NO injection happens. The LLM sees no past context. Garbage low-confidence matches make hallucination MORE likely; the strict threshold is intentional.

`embedder` is the SAME instance used at write time. Mixing embedders silently corrupts retrieval; the framework tags entries with `embedderId` and filters on read.

## A worked replay

```ts
import { Agent } from 'agentfootprint'
import { defineMemory, MEMORY_TYPES, MEMORY_STRATEGIES, SNAPSHOT_PROJECTIONS } from 'agentfootprint/memory';
import { anthropic } from 'agentfootprint/providers'; // vendor-SDK providers live on this subpath

// Monday — production decision
const monday = Agent.create({ provider: anthropic({...}), model: 'claude-sonnet-4-5-20250929' })
  .system('You decide loan applications based on credit + income + amount.')
  .memory(causal)  // CAUSAL × TOP_K × DECISIONS
  .build();

await monday.run({
  message: 'Should we approve application #42? Credit: 580. Income: 95k. Amount: 50k.',
  identity: { tenant: 'lending', conversationId: 'app-42' },
});
// → "Application #42: REJECTED. Credit (580) below floor (600). Suggest manual review."

// (a v2 snapshot is persisted automatically: the decisions, tool calls and
//  accounting observed in this run's component execution leg)

// ─── Friday — different user, different conversation ──────────────────

const friday = Agent.create({ provider: anthropic({...}), model: 'claude-haiku-4-5-20251001' })
  // ↑ NOTE: cheap follow-up model. It reads Monday's recorded evidence of
  //   one execution leg, possibly partial; the projection says which.
  .memory(causal)  // same definition, different agent instance
  .build();

await friday.run({
  message: 'Why was application #42 rejected?',
  identity: { tenant: 'lending', conversationId: 'app-42-followup' },
});
// → "Application #42 was rejected because credit score 580 was below
//    the threshold of 600."
```

The Friday agent's prompt includes Monday's run as the `DECISIONS` projection: the header and the leg-only limit sentence, the availability status, the recorded decisions, the tool evidence (here `lookupCreditBureau({"applicationId":"42"}) → { "score": 580, … }`) and Monday's final answer. The follow-up is grounded in what was recorded about that leg rather than in reconstruction — and the model is told that anything the leg did not record is unknown.

## Why this works — cheap-model triage

A trace recorded from your expensive production model is an *input* a smaller, cheaper model can read when it answers follow-up questions about that run. Reading recorded evidence is a smaller job than re-deriving the answer from the raw history, so a smaller model may be enough. This page states no cost or accuracy figure for that: no checked-in bench measures one. What the smaller model reads is the evidence of one component execution leg, possibly partial — not the whole of the agent's reasoning — and the projection tells it so.

This is the second of the three downstream consumers fanning out of one recording (see the hero diagram above): **cheap-model triage**.

## The third downstream consumer — training data export

The same JSON snapshot shape feeds SFT / DPO / process-RL training pipelines. Production traffic becomes labeled trajectories with zero extra instrumentation:

- Every successful customer interaction → positive trajectory
- Every escalation / override → counter-example
- Every `decide()` evidence → the supervision signal for process-RL
- Every `select()` rationale → the verbal explanation that DPO/RLAIF needs

The export API (`causalMemory.exportForTraining({ format: 'sft' | 'dpo' | 'process-rl' })`) is roadmap work — tracked in [GitHub issues](https://github.com/footprintjs/agentfootprint/issues). The snapshot shape that makes it possible is shipping today; the export wrapper is the missing 200 lines.

**One recording, three economics.**

## Anti-patterns

- ❌ **Don't fall back to top-K-anyway when threshold misses.** The library throws by design; garbage past context is worse than no context.
- ❌ **Don't change embedders between writes and reads.** The framework tags + filters, but only if you respect the contract.
- ❌ **Don't use `FULL` projection by default.** It's the largest payload; reserve for forensic-grade scenarios. `DECISIONS` carries the same decisions and tool evidence in a smaller form.
- ❌ **Don't share the causal store across tenants.** The `MemoryIdentity` tuple namespaces, but only if you pass per-tenant identity at every `agent.run()` call.

> A user asks your refunds agent to approve order A-1001. It does. The next message is **"why did you approve it?"** Without an API, your only move is to paste the whole trace into another LLM and pay full price for it — every turn. `.selfExplain()` makes it one builder call: the agent answers the follow-up **from its own recorded run**, not from "memory of memory."

## It stays out of the way until asked

`.selfExplain()` mounts **one skill**. Day to day the tool catalog carries only that skill's activation row — your production tools are untouched, and the model never sees the trace tools. When the user asks "why…", the LLM activates the skill (`read_skill`), and **that iteration alone** gains the trace tools, late-bound to the previous run:

- `run_overview` — the catalog of what ran (steps, stages, loops, errors, honesty markers, and what the run cost)
- `find_context_errors` — **what did this run contradict itself about?** The Context Integrity findings the library already caught, each with the step it was filed at and the drill that opens the state behind it. When no finding evidence was captured it says so — never "no errors found", and a green verdict is printed only when the checker rows sum to at least one *checked* encounter. Its `kind` filter offers exactly the classes this build ships a check for (see [the tool reference](#find_context_errors--what-the-run-contradicted-itself-about) below).
- `find_in_trace` — **free text in, step ids out.** The user's words ("order 7712") searched across stage names, state keys, every committed value and the narrative; each hit line ends with the exact call that opens it. The first move when the question names something you have no id for.
- `trace_node` — inspect one step by id (its reads / writes / data + control parents / errors)
- `who_wrote` — which step last wrote a value (backtrack a key to its source)
- `get_value` — fetch **one** value by id + key, lazily — only the piece it needs, never the whole trace
- `trace_slice` — the backward causal slice around a node
- `backtrack` — variable-first: why is `K` what it is, and (with `element`) which step produced `K[i]`
- `inspect_tool_call` — **one tool call end to end**: the args the model *proposed*, the args it actually *ran with* (they differ when a governance rule rewrote them), the result, the outcome, the duration, and the step that ran it
- `inspect_tool_run` — **inside** one tool call, when that tool kept its own record (see [Through the tool boundary](#through-the-tool-boundary) below)
- `read_narrative` — the run's plain-English story, paginated

So the cost model is honest: the production catalog stays clean, and the trace tools appear **exactly once**, on the iteration where the question was asked. The example prints the per-call catalog to prove it.

Eleven definitions is a real bulge on the tools slot for that one iteration. The 2000-char `contextBudget.tools` default is a **signal, not a limiter** (nothing is ever truncated) — an agent that opts into `.selfExplain()` should raise it: `contextBudget: { tools: 7000 }`.

The same is true of the bytes. The toolpack is the largest single module in the library, and since 9.94.0 it is loaded through a dynamic `import()` **on the first iteration the skill is active** — not at `build()`, not on a turn where nobody asked why, and never for an agent that did not call `.selfExplain()`. A bundler puts it in its own chunk, so a browser consumer who imports `Agent` does not ship it; Node loads it through the same `require` one microtask later. Nothing about the run changes with the load: the catalog on an idle iteration is still answered synchronously, and a cold mount and a warm one record the same events in the same order (`test/lib/trace-toolpack/lazyMount.test.ts` pins both; `browserGraph.test.ts` fences the bundle graph).

## Through the tool boundary

`inspect_tool_call` used to end at a wall:

```
⚠ boundary: what happened INSIDE the tool is not traced — this is the envelope
  (arguments in, result out) plus what the run itself decided about it.
```

That is the true answer for a tool that reaches into someone else's system. It was needlessly true for a tool that **is** a footprintjs flowchart: that tool recorded every stage it ran, and then threw the recording away, because nobody was holding it.

`flowchartAsTool({ keepRecord: true })` holds it. Each invocation's inner record is filed under the `toolCallId` the outer run already uses to name that call, so the wall becomes a rung:

```
inside: this tool kept its own record of the run — 4 step(s), ok.
        Descend with inspect_tool_run({ toolCallId: 'c1' }).
```

`inspect_tool_run` then opens that inner run with the **same drill vocabulary**, one level down — the inner views are the pack's own tools run over the inner artifacts through `openRecording`, so there is no second implementation to drift:

```ts
inspect_tool_run({ toolCallId: 'c1' })                                  // the inner run's overview
inspect_tool_run({ toolCallId: 'c1', find: 'rain' })                    // free text → INNER ids
inspect_tool_run({ toolCallId: 'c1', variable: 'advice' })              // why is this inner value what it is
inspect_tool_run({ toolCallId: 'c1', runtimeStageId: 'validate#1' })    // one inner step
inspect_tool_run({ toolCallId: 'c1', runtimeStageId: 'validate#1', key: 'rainChancePct' })  // the field, in full
```

Four things keep it honest:

- **Off by default.** A retained record is retained memory. `keepRecord` is the caller agreeing to it; `keepRecordLimit` (default 20) bounds it as an LRU window, and a session that dropped older records **says so** rather than answering "not found".
- **Two id namespaces, said out loud.** Inner `runtimeStageId`s name steps of the *tool's* chart, not of the run that called it. Every answer repeats that, and the outer `trace_node` / `get_value` do not accept them.
- **Honest absence names the switch.** With no record kept, `inspect_tool_run` names `keepRecord` and points back at the envelope — it never answers emptily.
- **Redaction still governs — the whole record, not only its log.** footprintjs scrubs at commit time, so a key covered by `flowchartAsTool`'s `redact` policy never enters the inner commit log at all; and since 9.89.1 the kept record's `sharedState`, its subflow states and the string the tool returns are all served from the same redacted view (one owner, `servableSnapshot`), so a kept record cannot serve what the policy removed from any field, and the `(redacted by policy)` flag reads the same inside a tool as outside one. Under a policy the record omits `initialState` — footprintjs's own rule for the redacted view — so a fold of it reports `basis: 'log-only'`.

One thing an inner record carries that a saved recording never can: **control edges**. The record is live in process, so the wrapping tool attaches a fresh `controlDepRecorder()` per invocation and inner slices show the decision rule that routed execution — `← [control: Rain chance at or above the 60% bike threshold]`.

The builder does the wiring: `.build()` collects the store off every statically registered (and skill-declared) chart tool and hands one merged lookup to the trace artifacts. A chart tool delivered through a `.toolProvider()` is resolved per iteration and therefore not collected at build time — register it statically as well if you want the descent.

### Wiring it by hand

Assembling artifacts yourself (a scripted auditor, a custom debugger, a chart tool mounted outside an Agent)? The store is a small, exported piece of machinery, and `TraceToolpackArtifacts` takes it as an optional `innerRuns`:

```ts
import {
  innerRunsOf, innerRunStore, mergeInnerRuns, traceToolpack,
} from 'agentfootprint/observe';

const records = innerRunsOf(adviceTool)!;               // the store the tool is holding
const tools = traceToolpack({ snapshot, innerRuns: records });
```

- `innerRunsOf(tool)` reads a tool's store, or `undefined` when it keeps none. It is **total** — a plain tool, a string, `null` all answer "no records" rather than throwing. It finds the store under `INNER_RUN_RECORDS`, a registry symbol rather than a named property, so a consumer's own tool cannot collide with it.
- `innerRunStore(limit?)` builds one directly (an `InnerRunStore`: the read side plus `keep`). `DEFAULT_INNER_RUN_LIMIT` is that default of 20; a limit below 1 is clamped, because a store that keeps nothing is `keepRecord: false` said with a number that lies.
- `mergeInnerRuns(lookups)` composes several stores into one `InnerRunLookup` — an agent may mount more than one chart tool, and the model asking to descend into a call should not have to know which tool produced it. An empty list gives `undefined`, not an empty lookup that would answer "nothing was kept" when the truth is "nothing keeps anything".
- An `InnerRunRecord` carries the `toolCallId`, the `toolName`, an `InnerRunOutcome` (`'ok' | 'error' | 'paused'` — a failed inner run is still a complete record), the step count, the `{ snapshot, structure }` recording, the live control-dependence lookup, and — if capture itself failed — the `problem` that explains why there is no recording. `InnerRunSummary` is that row without the recording, which is what the unknown-id correction lists. `KeepsInnerRuns` is the structural type of a tool carrying a store.

Worked end to end in [`examples/features/50-through-the-tool-boundary.ts`](https://github.com/footprintjs/agentfootprint/blob/main/examples/features/50-through-the-tool-boundary.ts): a weather-advice agent answers "why did you say it'll rain?" by descending into its own tool and citing the inner stage plus the exact field — with the chart's stage counters printed either side to prove nothing re-executed.

## What one captured turn carries

A snapshot alone cannot answer everything. The binding captures three things at the same terminal flush, so all three describe one turn: the **snapshot**, the run's **narrative** (what `read_narrative` pages through), and a bounded **tail of the run's typed events** (the only clock a run has — what `inspect_tool_call` reads durations from, and where the Context Integrity findings `find_context_errors` serves live). Both optional parts default **on**; with `events: false`, `find_context_errors` reports the evidence channel as *absent* rather than reporting a clean run:

```ts
.selfExplain({
  include: { narrative: true, events: true },  // SelfExplainInclude — both default true
  maxEvents: 2000,                             // per-turn tail cap (SELF_EXPLAIN_MAX_EVENTS)
})
```

`maxEvents` caps the retained tail per turn; its default is exported as `SELF_EXPLAIN_MAX_EVENTS` (2,000 — enough for a long tool-using turn, small enough that a server holding one binding per agent does not grow without limit), and a tail that dropped events says so rather than letting a reader mistake the remainder for the whole turn. `include` takes a `SelfExplainInclude` — two booleans, both defaulting to `true`, because the tools that read these parts are on the catalog either way and a tool that answers "⚠ no evidence" by default is a tool that teaches the model not to call it. Turn one off when the cost matters more than the answer. `events: false` makes **no** wildcard event subscription at all, rather than one that is ignored; a tool whose evidence is missing then says which switch turns it back on instead of answering emptily. (`SelfExplainSource` is the shape the builder hands the binding — all three sources in one call, so no wiring can be half-done.)

**One agent, many people.** Evidence is kept per conversation, never per instance: on an agent shared by many sessions (`standingAgent({ agent })`), "the previous completed run" is the asking conversation's, not whoever ran last. The source's `getServing()` answers a `SelfExplainServing` — which conversation the run in flight belongs to, and which run it is. A run with a session is keyed by its session; a request `standingAgent` serves without one is keyed by a random id minted for that request, in a key space no session id can enter; only a direct run with no session shares the no-session key. A tool's kept records are served only to the conversation whose runs filed them — including a run that paused or failed.

## How we know it's faithful (the guarantee)

The point of self-explanation is to *not* inherit the unfaithfulness it's meant to diagnose. Two invariants make that real:

1. **It can never answer about an in-flight run.** `Agent.run()` reassigns its executor at the *start* of a run, so reading the "current" snapshot mid-run would expose the unfinished turn. The binding sidesteps this by capturing the snapshot **only at terminal flush** — `onRunEnd` / `onRunFailed`. There is no code path that hands the model an in-progress trace; it physically can only see a *completed* run.
2. **A failed run is still explainable.** Capture fires on `onRunFailed` too, so **"why did you fail?"** works — the error and the trace up to it are recorded evidence.

Two more details that keep it correct: a **fresh control-dependence recorder per run** (so "which decision allowed this step?" survives the per-run id reset and stays valid for the whole follow-up turn), and — before the first completed run — a plain "no completed run yet" message instead of an error. Every answer cites step ids you can re-open with the same tools, so the explanation is checkable, not asserted.

## `.selfExplain()` vs. Causal memory — which "read its own trace"?

Both let the agent answer "why?" from the trace, but they pull at different ranges — use them together:

| | **`.selfExplain()`** | **[Causal memory](doc:causal-deep-dive)** |
|---|---|---|
| Answers about | the agent's **previous run** (this conversation) | **any past run**, retrieved across sessions |
| Selected by | the user asking, *now* | semantic similarity to the new question |
| Persisted? | no — in-memory, the last completed run | yes — to the configured store (survives restarts) |
| Granularity | drills to one piece, by id, on demand | recalls a whole past run's snapshot |
| Reach for it when | a follow-up in the *same* conversation | "why did you decide X *last week / in session Y*?" |

Mental model: **Causal memory pulls the right *run*; `.selfExplain()` drills the right *piece* of it.** Both are lazy — only what's needed, only when asked. (Stacking them — recall a stored run, then drill it with the trace tools — is the in-progress "evidence bridge"; see [Causal memory deep-dive](doc:causal-deep-dive).)

## Gotchas

- **Needs `reactMode: 'dynamic'`** (the default) or `'dynamic-grouped'`. `'classic'` caches the tools slot on turn 1, so a mid-turn skill activation could never surface the trace tools — `.selfExplain()` **fails loud at build** rather than silently never answering. (Need it on a classic-mode agent? Run `traceDebugAgent()` as a separate session instead.)
- **Reserved tool names.** Inline mode reserves all eleven names the pack can mount — `run_overview` / `find_context_errors` / `find_in_trace` / `trace_node` / `trace_slice` / `backtrack` / `who_wrote` / `get_value` / `inspect_tool_call` / `inspect_tool_run` / `read_narrative`; delegate mode reserves `explain_run`. The tools slot dedupes by name (first wins), so a consumer tool with one of those names would silently shadow the trace tool — `.build()` throws to stop it. The list is read from `TRACE_TOOL_NAMES` (the pack's own export) rather than retyped beside it, so it cannot fall behind the pack.

## Without `.selfExplain()` — the toolpack and a dedicated debugger

`.selfExplain()` is one of three doors over the same tools. The other two take the evidence of a completed run as a plain object — a `TraceToolpackArtifacts` bag — and work on any agent, including a `'classic'`-mode one:

- `traceToolpack(artifacts, options?)` returns the raw tools. Mount them on any agent, or drive them from a script with `callTraceTool(tools, name, args)` — it validates the arguments against the tool's schema first, exactly as an Agent would, and returns the same correction string on a bad call instead of executing.
- `traceDebugAgent({ artifacts, provider, model })` returns a ready `Agent` whose whole catalog is the toolpack and whose system prompt is the debugging method (overview → drill by id → cite evidence → respect ⚠). Options: `maxIterations` (default 8), `instruction` (appended to the method), `toolpack` (the bounding dials), `name`.

```ts
import { recordRun, openRecording, traceToolpack, callTraceTool, traceDebugAgent } from 'agentfootprint/observe';
import { anthropic } from 'agentfootprint/providers';

const recorder = recordRun(agent);
await agent.run({ message: 'Approve loan APP-7' });
const artifacts = openRecording(recorder.toRecording());   // { snapshot, events, … }

// Scripted — the offline auditor pattern:
const tools = traceToolpack(artifacts, { valueMaxChars: 4000 });
console.log(await callTraceTool(tools, 'run_overview'));

// Conversational — a cheap model, in a session of its own:
const debuggerAi = traceDebugAgent({ artifacts, provider: anthropic(), model: 'claude-haiku-4-5' });
await debuggerAi.run({ message: 'Why was loan APP-7 approved?' });
```

The bag has one required field and four optional ones. Each optional one switches on something, and a tool whose evidence is missing says so rather than answering emptily:

| field | what it is | what it adds |
|---|---|---|
| `snapshot` | the run's snapshot (`agent.getLastSnapshot()`) | everything — the commit log and execution tree every tool reads |
| `controlDeps` | footprintjs's `controlDepRecorder().asLookup()` from the run | `[control: rule]` edges in slices; without it, slices carry `⚠ control edges unavailable` |
| `narrative` | the narrative lines | the `read_narrative` tool (it is not mounted without them) |
| `events` | the run's typed events | `inspect_tool_call` durations and outcomes, and every `find_context_errors` finding |
| `innerRuns` | the records chart tools kept (see [Wiring it by hand](#wiring-it-by-hand)) | `inspect_tool_run` |

Runnable: [`examples/observability/01-trace-debug-session.ts`](https://github.com/footprintjs/agentfootprint/blob/main/examples/observability/01-trace-debug-session.ts) (scripted) and [`examples/observability/07-trace-debug-agent.ts`](https://github.com/footprintjs/agentfootprint/blob/main/examples/observability/07-trace-debug-agent.ts) (the dedicated debugger).

## The tools, one by one

Every step id is a `runtimeStageId` — `stageId#executionIndex`, for example `normalize#1`. The `#index` counts across the whole run, not per stage. It is the one key that links the commit log, the execution tree and the events, and every tool that takes a step accepts it.

| tool | parameters | answers |
|---|---|---|
| `run_overview` | — | What happened, broadly: status, every stage (id, name, description), loop counts, where errors appeared, honesty notes, and cost when the run priced itself. **Start here.** |
| `find_context_errors` | `kind?`, `limit?` (default 10, cap 25) | What did the run contradict itself about? The integrity findings already filed. |
| `find_in_trace` | `query`, `maxHits?` (default 10, cap 25) | Where does this text appear? Free text in, step ids and keys out. |
| `trace_node` | `runtimeStageId` | What did step X write (bounded previews plus true sizes), read, and where did its inputs come from? |
| `trace_slice` | `runtimeStageId`, `key?`, `maxDepth?` (default 6, cap 20), `maxNodes?` (default 25, cap 100) | Which chain of steps produced the data at X, as an indented tree of drillable ids? |
| `backtrack` | `variable`, `element?`, `before?`, `maxDepth?`, `maxNodes?` | Why is variable K what it is? No step id needed. `element` asks which step produced `K[i]`; `before` (a commit index) explains the value as it stood before that point. |
| `who_wrote` | `key`, `beforeStageId?` | Which step last wrote K (optionally, strictly before step Y)? |
| `get_value` | `runtimeStageId`, `key`, `maxChars?` (default 2000, cap 8000) | The full value of K as of step X. It works on delta commit logs. |
| `inspect_tool_call` | `toolCallId` | One tool call, end to end. |
| `inspect_tool_run` | `toolCallId`, `find?`, `variable?`, `runtimeStageId?`, `key?` | Inside one tool call, when the tool kept its own record. |
| `read_narrative` | `offset?`, `maxLines?` (default 40, cap 200) | The run's story, one page at a time. |

The defaults come from `TraceToolpackOptions` (`previewChars`, `sliceMaxDepth`, `sliceMaxNodes`, `valueMaxChars`), which you pass as the second argument to `traceToolpack` or as `toolpack` on `traceDebugAgent` and `.selfExplain()`. The caps are `TOOLPACK_HARD_CAPS`, and no argument can go past them.

### `find_context_errors` — what the run contradicted itself about

When an answer looks wrong, the cheapest move is to ask whether the library already caught the problem. Every [Context Integrity](doc:context-integrity) check files its findings on the run's event stream. This tool reads them. It never re-runs a check and never re-judges one. What it adds is the join: the step each finding was filed at, and the next call to make.

```
CONTEXT ERRORS — 1 finding(s) filed by this run's integrity checks (showing 1 of 1).

[1] dangling-reference @compose · iteration 4 — 'screen_fire' is being offered while the
    results that ground its arguments have left the window (whats_here) …
    about: tool:screen_fire, tool:whats_here → find_in_trace('screen_fire')
    filed at call-llm#88 → trace_node('call-llm#88') · trace_slice({ runtimeStageId: 'call-llm#88' })

CHECKERS (posture: observe · …):
- dangling-reference @compose: ran 6× · 6 finding(s) · not-applicable 3 (out of scope by rule)
```

(Abridged.) What to know:

- **The checker rows are part of the answer.** "The checks ran and found nothing" and "no check was registered here" are different facts. A clean verdict is printed only when the rows add up to at least one *checked* encounter. If every encounter was out of scope or unreachable, the answer is **⚠ NOTHING WAS CHECKED**, with the reason.
- **Absence has its own wording.** With no `events` in the bag, the tool reports *no finding evidence*, not a clean run. When the checker rows count findings the event tail no longer holds, it says **⚠ EVIDENCE MISSING**.
- **`kind` offers only classes a check in this build can file:** `invariant-violation`, `unsupported-argument`, `dangling-reference`, `unsupported-claim`, `empty-lookup`, `column-type-mismatch`, `missing-column` and `prior-turn-evidence`. The finding type also names `duplicate-execution`, but nothing files it. The tool says so rather than answering "none found" about a class nobody checks.
- **Findings are deduplicated when they are filed**, so a defect found again on a later iteration counts once. If the rows count more encounters than the list shows, the output says so.
- **Findings are drillable.** The step a finding was filed at is a real `runtimeStageId`. An id that is not a step in this run is marked ⚠ instead of being offered as a drill.

### `inspect_tool_call` — the four records, joined

A tool call is spread across four records: the args the model *proposed* are on an assistant turn, the args it actually *ran with* are in the middleware ledger (only when a rule changed them), the result is a `role: 'tool'` turn, and the timing exists only in the event stream. This tool joins them for one `toolCallId`:

```
TOOL CALL c2 — check_inventory
step: tool-calls#22 — drill with trace_node('tool-calls#22')
proposed by the model: {"sku":"KB-88"}
ran with: {"sku":"KB-88","limit":5} — CHANGED at before-tool by 'clamp-limit': "page size capped at 5"
result: "Stock for KB-88: 12 units available…"
outcome: ok
duration: 4ms
```

The proposed/ran-with split is the reason it exists. A [middleware](doc:middleware) rule that rewrites args does not show up in the conversation: the model sees its own proposal in the history, and the tool ran with something else. Outcomes are `ok`, `error`, `denied` or `paused`. Without `events` in the bag, the line reads `duration: ⚠ unavailable` and explains that the commit log has no clock. An unknown id gets a correction that lists the ids this run actually recorded.

For a tool that reached into someone else's system, the answer ends at the tool boundary — what went in and what came back. A tool can push that further by returning its own diagnostic refs (a request id, a log link), which travel through the trace like any other result. A chart tool with `keepRecord: true` goes further still: see [Through the tool boundary](#through-the-tool-boundary).

## The contracts

- **Bounded by default.** Previews are capped, slices have depth and node budgets, and values have character budgets. The model can raise a budget per call, but only up to `TOOLPACK_HARD_CAPS`. A value cut short says so: `⚠ truncated: served N of M chars`.
- **Honest, never silent.** A truncated slice is marked, and so is a step that consumed inputs the commit log cannot see (run args, env, untracked reads). A missing `controlDeps` lookup, missing read tracking and values that never enter the commit log (pre-run state, values carried in closures) are named, not left out. `who_wrote` on a key with no tracked write says the value may have come from one of those places. It does not say "nothing wrote it".
- **Redaction-respecting.** footprintjs scrubs the commit log at commit time. The tools pass the placeholders through as they are, flag the key `(redacted by policy)`, and never reconstruct around a redaction.
- **Strict schemas.** On a small run (48 steps or fewer), step-id parameters carry an `enum` of every real step id, so a made-up id is rejected before the tool runs and the model corrects itself. Key parameters have **no** enum on purpose: a question about a key outside the commit log has an honest answer ("args, env and pre-run values never enter the commit log"), not a validation error. A bad id that gets through returns a correction naming the real steps.

## Security posture

Trace content can carry **adversarial text from the original run**. Tool results, retrieved documents and user input all pass through state, and these tools serve them back, bounded. Showing trace content to a model therefore shows it any prompt injection the run contained (see [Security](doc:security#prompt-injection--what-the-library-does-and-does-not-do)).

- Prefer a **separate session over a completed run** — `traceDebugAgent`, or `.selfExplain({ delegate })` — to trace tools mounted on the production agent. Delegate mode keeps the trace walk out of the production context; only the bounded, cited answer comes back, as a tool result.
- Treat what the tools return as **data, not instructions**. The bounded views limit how much comes back. They do not clean up what it says.
- The toolpack never re-runs anything and holds no credentials. It is a read-only view over frozen artifacts.

## Token economics

[`examples/observability/01-trace-debug-session.ts`](https://github.com/footprintjs/agentfootprint/blob/main/examples/observability/01-trace-debug-session.ts) plants a wrong value (a debt-to-income ratio computed against annual instead of monthly income) that flows through a `decide()` decision. A scripted debugger finds the culprit step in 8 tool calls, served about 2.8K characters, against a full trace dump (snapshot JSON plus narrative) of about 29K — roughly a tenth. The gap grows with run size, because a session costs what the model *opens*, not what the run *produced*. The example prints its own numbers, so run it to see them for your build.

## Explaining a run that already finished

`.selfExplain()` answers about the agent's *previous* turn, in memory. For a run recorded weeks ago, `openRecording` reopens a saved `recordRun` bundle — `{ snapshot, events, structure }`, live or parsed back from JSON — as the same artifacts the trace tools navigate:

```ts
import { recordRun, openRecording, traceToolpack, callTraceTool } from 'agentfootprint/observe';

const tools = traceToolpack(openRecording(JSON.parse(fs.readFileSync('run.json', 'utf8'))));
await callTraceTool(tools, 'find_in_trace', { query: 'order 7712' });
```

It is pure — no engine, no agent, no I/O — and takes an `OpenableRecording` (any bundle structurally matching a `Recording`). It is honest about the two things a serialized run cannot carry back: `controlDeps` is a lookup *function* and does not serialize, so slices carry the existing `⚠ control edges unavailable` marker; and the narrative survives only if a narrative recorder was attached at record time, since `recordRun` deliberately attaches none. A bundle with no snapshot, or a snapshot missing `commitLog` / `executionTree`, is refused with a message naming `recordRun` as the producer.

> Your agent gave the wrong answer. The trace shows you *what* happened — every injection, every tool call, every token. It doesn't show you *which one of them caused it.* That's a different question, and the one you actually need answered at 2 AM.

## What observability can't tell you

[Observability](doc:observability) answers **what happened**: which fact was injected, which tool ran, what the model returned. But when the answer is wrong, you're left scrolling a trace asking *which piece of context did this?* — and a trace, however detailed, only **correlates**. It can't tell you that *removing* the suspect would have fixed it.

That's a debugging problem, not a logging problem. So we built a debugging harness for it.

<Callout type="info" title="Debugging, not evaluation">
*Evaluation* grades many scenarios at scale — *does the agent pass?* — the development-phase harness you build before shipping. *Debugging* takes the **one** output that failed and finds **why**, then proves it. The book draws the same line: *"a single scenario is useful for debugging, but real evaluation requires scale."* This guide is the **debugging** half — it hands you the backtrace and a trigger to connect a failed case to its cause. The **grader is yours**: we ship the machinery, not a built-in judge. (For production monitoring, see [Observability](doc:observability).)
</Callout>

## Git bisect for context

`localizeContextBug` is **git bisect for context**. Point it at the step that went wrong; it walks the run backward to the inputs that fed that step, ranks them, and — if you give it a way to re-run — **tests** each one by removing it and watching whether the answer flips.

Five stages, all over the run you already recorded:

1. **Trigger** — the step that's wrong (the answer-producing LLM call, an explicit step, a custom rule, or the lowest-quality step).
2. **Slice** — walk the commit log backward from the trigger (data **and** control edges) to everything that fed it.
3. **Weigh** — score how strongly each LLM-call edge pulled on its inputs.
4. **Rank** — turn the slice into ablatable suspects (tool / injection / memory / arg), ordered by influence.
5. **Ablate** — *optional, but the whole point:* re-run the scenario without each top suspect. If the answer flips, that's a **causal verdict**.

## Honesty first: ranking is a guess, ablation is proof

This is the line we hold that most tools blur. **The ranking is a proxy** — embedding geometry, not a causal claim. **Only the ablation verdict is causal**, because it's the only step that actually removed the thing and saw what changed. Every report says which mode it's in (`correlational` vs `causal`) and never dresses a guess up as proof.

So a report **without** a re-runner stops at a ranked list of suspects, honestly labeled `correlational`. Hand it a re-runner and the top suspects get **verdicts** — `confirmed` or `not confirmed`, with the flip count — and the report gets a **conclusion** that reads them together.

## Quickstart

Point the localizer at the answer-producing call and give it a re-runner so it can confirm suspects by ablation:

```ts twoslash
import { localizeContextBug, embeddingCache, formatContextBugReport } from 'agentfootprint/observe';
import { mockEmbedder } from 'agentfootprint/memory';
import type { ContextBugArtifacts, AblationSpec } from 'agentfootprint/observe';

// From a recorded run: the artifacts bag, the step that produced the bad
// answer, that buggy output, and a way to re-run with a suspect removed.
declare const artifacts: ContextBugArtifacts;
declare const answerStep: string;
declare const buggyOutput: string;
declare function rerunWithout(specs: readonly AblationSpec[]): Promise<string>;
// ---cut---
const report = await localizeContextBug({
  artifacts, // { snapshot, events } from the recorded run
  embedder: embeddingCache(mockEmbedder()),
  atStep: answerStep, // the step that produced the bad answer
  rerun: {
    // give it a re-runner → it confirms suspects by ablation
    runner: rerunWithout,
    originalOutput: buggyOutput,
    samples: 3,
    outcomeChanged: (a, b) => a.includes('APPROVED') !== b.includes('APPROVED'),
  },
});

console.log(formatContextBugReport(report));
```

The report's conclusion names the planted fact, and the decoy isn't confirmed:

```text
CONTEXT BUG LOCALIZATION — trigger call-llm#18 "CallLLM" (explicit)
mode: CAUSAL — ranked proxies + counterfactual ablation verdicts (verdicts are the only causal claims)
...
CONCLUSION (one-cause): Removing injection 'vip-override' flipped the answer, and removing the other tested items did not. The answer needed it here, which doesn't by itself show that it's wrong.

SUSPECTS (4, ranked by correlational proxy score):
 1. [injection 'vip-override'] — score 0.787
    verdict: NEEDED IN THIS CONTEXT: ablating injection 'vip-override' flipped the outcome in 3/3 seeded reruns. This doesn't by itself show it's the root cause.
 2. [injection 'style-rule']  — score 0.746
    verdict: NOT CONFIRMED: ablating injection 'style-rule' did not change the outcome in 3 seeded reruns.
```

Items that can't be removed, like a plain stage, are listed after the items that can, because they can't be tested. The harness doesn't trust the ranking anyway. It trusts the **verdict**: here, the planted fact is the one thing that changed the answer when removed.

The full runnable, tested example is [`17-localize-quickstart.ts`](https://github.com/footprintjs/agentfootprint/blob/main/examples/observability/17-localize-quickstart.ts) (and the fuller [`05-context-bisect.ts`](https://github.com/footprintjs/agentfootprint/blob/main/examples/observability/05-context-bisect.ts), with a tool suspect and a `decide()` control-edge walk).

## Read the conclusion

A `confirmed` verdict means the answer needed that item in this context. It doesn't by itself show the item is wrong. Reading verdicts one at a time can mislead in two ways:

- **A model's own mistake can look like several causes.** Removing a true fact the model needs can flip the answer, so correct facts get confirmed.
- **Two causes can look like none.** When two items are each enough alone, removing either one changes nothing.
- **One path can look like two causes.** A planted instruction can make the agent call the wrong tool. Removing either the instruction or the tool flips the answer, but the tool's result only came about because of a model call that read the instruction.

`report.conclusion` reads the verdicts together:

| `kind` | What happened | `named` |
|---|---|---|
| `one-cause` | One item flipped the answer when removed | That item |
| `one-path` | Several items flipped it, and the record shows they lie on one path | Those items, earliest first |
| `needed-together` | A few separate items each flipped it | Those items, highest ranked first |
| `redundant-pair` | No item flipped it alone, and exactly one pair did together | That pair |
| `missing-context` | No removal flipped it, and restoring a dropped unit did | Nothing. See `restored` |
| `no-single-cause` | More than a third of the items flipped it, or several pairs did | Nothing |
| `none-found` | Nothing tested flipped it | Nothing |
| `inconclusive` | The reruns disagree, or nothing was tested | Nothing |

<CodeFile path="examples/observability/26-localize-conclusion.ts" region="conclusion" title="examples/observability/26-localize-conclusion.ts" />

Things to watch for:

- **`none-found` doesn't mean there's no cause.** A cause may be in a larger group or outside the items tested. `statement` says what was tried, including how many ranked items weren't tested.
- **The pair search costs model runs.** When no single removal flips the answer, it tries every pair among the top 5 items. That's up to 10 more probes, each costing `samples` runs, so 30 runs with the default of 3 samples. Set `rerun.pairSearchTop` to change how many items it pairs, or to `0` to turn it off.
- **The cut-off is a default, not a law.** Set `rerun.maxFlipShare` to change the one-third limit. A larger model may need a different value than a small, fragile one.
- **`needed-together` can include an innocent item.** Removal alone can't tell a true fact the answer leaned on from a second real cause, so check them in order.
- **`one-path` doesn't say which link is wrong.** The earliest item isn't always the fault. A correct instruction can lead to a tool that returns bad data. `conclusion.links` shows each link: `code` means only fixed steps lie between the two items, and `model-or-tool` means the later one came after a call that read the earlier one, which shows it could have depended on it, not that it did.

For a search over larger groups, pass the ranked suspects to `bisectCulprits`.

## Correlational vs causal — pick your cost

Ablation re-runs your scenario N times, so it costs N runs. Skip the re-runner and you get the ranked slice for free — useful triage, honestly labeled a guess. Add the re-runner when you need proof.

## Choose a scoring strategy

The **rank** stage is a named, swappable strategy. Two ship: **`semantic-alignment`** (the default — embeddings, the four-signal composite; needs an embedder) and **`lexical-overlap`** (plain word overlap; free, deterministic, no dependencies). A strategy only **reorders suspects** — ablation alone convicts — so any of them is safe to swap in.

`listInfluenceStrategies()` is exactly what a host UI's strategy picker needs. Each strategy carries `requirements` so the selector can grey out what the host can't run:

```ts twoslash
import { listInfluenceStrategies } from 'agentfootprint/observe';

// Build a selector: grey out what the host can't run.
const hostHasEmbedder = false;
const options = listInfluenceStrategies().map((s) => ({
  name: s.name, // 'semantic-alignment' | 'lexical-overlap'
  description: s.description,
  disabled: s.requirements.includes('embedder') && !hostHasEmbedder,
}));
```

Pass a strategy to `localizeContextBug({ scorer })` — the report's `rankedBy` echoes which one ranked (a bare `InfluenceScorer` function still works; it reports `'custom'`):

```ts twoslash
import { localizeContextBug, embeddingCache, lexicalOverlapStrategy } from 'agentfootprint/observe';
import { mockEmbedder } from 'agentfootprint/memory';
import type { ContextBugArtifacts } from 'agentfootprint/observe';

declare const artifacts: ContextBugArtifacts;
declare const answerStep: string;
// ---cut---
const report = await localizeContextBug({
  artifacts,
  embedder: embeddingCache(mockEmbedder()),
  atStep: answerStep,
  scorer: lexicalOverlapStrategy, // free, deterministic word overlap
});

report.rankedBy; // 'lexical-overlap'
```

Once you have a ranking, [re-run without a source](doc:rerun-without-sources) to prove it.

## When you don't know which step is wrong

`atStep` is the explicit door. Two others:

- **Custom trigger** — `trigger: (artifacts) => stepId`: your own rule for "which step looks wrong."
- **Quality-driven** — attach a `QualityRecorder` and the localizer defaults to its lowest-scoring step.

### Bring your own judge

The quality-driven trigger is where you plug in a score. Attach a `QualityRecorder` with **your** scoring function — an LLM-as-judge, a schema check, a regex assertion — and the localizer starts the bisect at the lowest-scoring step. Two honest notes:

- **The score is a guess, not a verdict.** The lowest-scoring step is *where to start looking* — correlational. Only the ablation that follows is causal. We ship the scoring machinery, not the judge: there is **no built-in metric**.
- **The scoring function is synchronous.** It can't `await` an LLM judge inline — pre-score into a map (or judge after the run and feed a custom lookup), then return the number.

The standalone *quality stack trace* — `qualityTrace` / `formatQualityTrace`, which renders the score-annotated backtrace — is a footprintjs primitive. See [Backward causal chain](https://footprintjs.github.io/footPrint/blog/backward-causal-chain/).

## Other debugging doors

Same engine, different entry points (all beta):

- **finders** — `traceSteps` (dependency-guided backward search), `removeAndRetry` (leave-one-out ablation), `shrinkToCause`.
- **`bisectCulprits`** — search for the smallest set of suspects whose removal together flips the answer.
- **`walkToRoot`** — walk a symptom backward across loop iterations to the true root cause (see [Read the run loop-by-loop](#read-the-run-loop-by-loop) below).
- **missing context** — supply what was *available* vs what was *sent*; restoring a dropped unit that flips the answer is the mirror of ablation (also causal).

## Read the run loop-by-loop

When the bug isn't in the last step but a few iterations back, read the run as a **trajectory**. `assembleTrajectory(artifacts)` slices a ReAct run into one **`LoopFrame` per iteration** — each carrying its LLM call, the context that fed it, and where its tool output came from. `walkToRoot` is just `walkTrajectory(assembleTrajectory(...))`: it walks that per-loop structure backward from the symptom to the iteration that planted the cause.

This is the **same substrate** the localizer already walks — a structured view of the run, not a score. There is no trajectory *grade* here: "did the whole run succeed?" is a metric you supply. Runnable, tested examples: [`13-per-loop-trajectory.ts`](https://github.com/footprintjs/agentfootprint/blob/main/examples/observability/13-per-loop-trajectory.ts) and [`15-walk-to-root.ts`](https://github.com/footprintjs/agentfootprint/blob/main/examples/observability/15-walk-to-root.ts).

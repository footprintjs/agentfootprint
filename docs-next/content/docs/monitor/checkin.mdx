> An agent is about to issue a $5,000 refund. You don't want a policy to silently allow or block it — you want a **person** to say yes, and you want them to see WHY the agent is asking: what it will do, what context it read, which context drove the choice. That's a check-in. **OpenWorker-class agents check in; agentfootprint checks in with the receipts.**

## Check-in vs. the other gates

Three independent gates run before a tool executes, in this order:

| Gate | Question | This guide? |
|---|---|---|
| **Permission** ([Security](doc:security)) | Is this call *allowed* by policy? | no |
| **Arg-validation** | Do the args match the schema? | no |
| **Check-in** | Does a *human* consent to this consequential action? | **yes** |

Permission is a policy engine (allow/deny/halt, no human). Check-in is **consent** — a human decides, with an evidence pack in front of them. A call the policy denies never reaches the check-in gate; a call awaiting consent never resolves credentials or executes.

## Declare the demand

A tool declares `checkIn` — `'always'`, or a `(args, ctx) => boolean` predicate for the "only high-effect" case. Configure the evidence pack on the builder with `.checkIn({ evidence })` (optional — `'standard'` is the default).

A tool WITHOUT `checkIn` is byte-identical to before — no gate, no events, no pause.

A predicate judges the arguments; it never changes them. It — like a `tool_start` listener, a permission checker's `context`, a custom evidence assembler, and the history they are handed — gets a frozen copy, never the object the tool runs with: one copy per call, shared (a call holding a `Map`, `Set`, `Date` or typed array gets one per callback, since freezing leaves those writable). A write throws in strict code (a predicate that throws trips the gate; a checker that throws denies) or is ignored in sloppy code; dev mode warns once per kind of callback. An approved call is held to its request again just before `execute`: arguments changed after the approval do not run.

## The ask carries the receipts

When the demand trips, `agent.run()` pauses BEFORE the tool executes and returns a `RunnerPauseOutcome` whose `checkIn` field is a typed `CheckInRequest`. `isCheckInPause(outcome)` distinguishes it from a plain `askHuman` pause.

<CodeFile path="examples/features/33-checkin.ts" region="ask" title="examples/features/33-checkin.ts (region: ask)" />

The `evidence` pack (`'standard'`) has four plain-named fields:

- **`willDo`** — a plain-words claim: the tool description + the rendered args.
- **`read`** — what context this run consumed, one frame per piece (`system` rules, the `task`, `result`s from earlier tools).
- **`drivers`** — which context drove THIS choice, ranked. The default scorer is deterministic and makes **zero LLM calls**; pass your own (e.g. an embedding-backed one wrapping `explainChoice`) via `.checkIn({ scorer })`.
- **`trail`** — a compact grouped run-so-far summary.

`evidence: 'minimal'` ships only `willDo` (zero cost). The whole pack survives `structuredClone` + JSON, so it can ride the checkpoint to another process.

### The ask can name the screen that collects the decision

Since 9.24.0 a tool can also declare **which registered frontend component** should collect its check-in decision — ids and props, never markup:

```ts
defineTool({
  name: 'issue_refund',
  description: 'refund a customer',
  checkIn: (args) => args.amount > 1000,
  checkInComponent: {
    componentId: 'approve-panel',       // your frontend's registry id
    props: { tone: 'serious' },         // small inline JSON
  },
  execute: ({ amount }) => `refunded ${amount}`,
});
```

It rides the `CheckInRequest` as `request.component` (and `PendingAsk.component` when the pause is served over a host). Declaring `checkInComponent` without `checkIn` is refused at `defineTool` — a component for a gate that never fires is configuration that lies. A `propsRef` here must resolve in the RUN's artifact scope when the gate trips; note a check-in fires **before** `execute`, so the tool cannot mint the ref mid-call — static declarations usually want inline `props`, and the mint-then-`askHuman` flow (see [Pause / Resume](/docs/monitor/pausable#typed-asks--a-registered-component-collects-the-answer)) is the door for big payloads.

## The decision is a record

The human answers with `checkInApproved({ request, by, note? })` or `checkInDeclined({ request, by, note? })` — `request` is the check-in they were shown, `outcome.checkIn` — and you `agent.resume(checkpoint, decision)`. On **approve** the tool executes normally (same iteration semantics as any resume); on **decline** the model receives `"declined by human: <note>"` as the tool result and adapts in-loop.

<CodeFile path="examples/features/33-checkin.ts" region="decide" title="examples/features/33-checkin.ts (region: decide)" />

Both the ask and the decision fire typed events — `agentfootprint.checkin.request` and `agentfootprint.checkin.decision` — that any recorder can observe via the emit channel, and the built-in `CheckInRecorder` captures them as a queryable audit trail (`getRequests()` / `getDecisions()` / `getStats()`). When the ask carried a `checkInComponent`, the decision event and the recorder's record additionally carry the `componentId` that collected the answer — the trace says which surface asked, while the decision itself stays the same structured fact.

### A decision answers one request, once

A "yes" is about one thing: the call the person was shown. So every check-in (and every middleware `ask`) mints a **request id** when it pauses — `outcome.checkIn.id`, `outcome.ask.id` — and the decision quotes it. The id is unique to that pause and bound to the exact call that runs on approval: the tool, its arguments, the call id, the served party and, for an ask, where the middleware chain resumes and the names of the rules from there on. On approval the tool runs with a detached copy of exactly those arguments; for an ask, a later link that hands back different ones gets the call refused rather than run.

Why it matters: without it, an approval is a bearer token for whatever is paused next. A duplicate click on "Approve" arrives after the first one resumed the run — and the run has since paused on a *different* refund the person never saw. A stored checkpoint whose arguments were edited after the ask still finds the person's yes. The same decision resumed twice runs the tool twice. Each of these is now refused, before the tool runs:

```ts
const out = await agent.run({ message: 'refund order 42' });
if (isCheckInPause(out)) {
  const decision = checkInApproved({ request: out.checkIn, by: 'maya@ops' });
  await agent.resume(out.checkpoint, decision);   // runs the refund
  await agent.resume(out.checkpoint, decision);   // ResumeDecisionError: 'already-answered'
}
```

`ResumeDecisionError` (`code: 'ERR_RESUME_DECISION'`) says which rule refused, in `reason` (a `ResumeDecisionRefusal`). It never names a request id — not in its message (which a host sends as the refusal's body), not on a field — because a refusal that named the paused request would hand a retrying client the one id it must not guess: the request to show the person is in the pending ask, never in an error.

| `reason` | The decision… |
|---|---|
| `'no-request'` | names no request — built by an older release, or by hand without `requestId` |
| `'request-not-recorded'` | can't answer this pause at all: the checkpoint recorded no request (written before requests were named) |
| `'other-request'` | names a different request — another conversation's, an earlier pause of this run, a parallel sibling's |
| `'call-changed'` | names this request, but the checkpoint's call changed after the ask (arguments, tool, call id, party, chain position, the rules recorded after the ask) |
| `'chain-changed'` | names this request (a middleware ask), but the agent resuming it runs other rules from the asking link on — one was removed, added, renamed or moved since (a redeploy) |
| `'already-answered'` | was already used by a resume — approved or declined; a decline spends the request too |
| `'closed-by-host'` | was closed by a host that kept the pause, because no answer could reach it any more — it spent the request, so its call did not run and no decision can run it |

All but `'already-answered'` and `'closed-by-host'` are refused before anything moves, and the checkpoint stays answerable with the right decision. A request is spent where the decision is used, in the resumed run, still before the tool. A composition (`Sequence`, `Parallel`, …) resumes its nested agents directly, so there every refusal comes from that same place.

`'request-not-recorded'`, `'call-changed'` and `'chain-changed'` are different: no decision changes them, so that pause can never be answered on that agent. Carrying the pause yourself, you abandon it (`agent.abandonPause()`) and ask again. A host that keeps it (`standingAgent`, `streamHandler`) closes it instead of letting it hold the session: the next message continues the conversation, the calls it left open recorded as not run only when the ledger the request was minted under spends the request itself (proof that no decision reached it, and that none ever can), else as possibly run ([Hosting](doc:hosting-and-runtime)).

Where answered requests are remembered is a `DecisionLedger`, and **"once" holds per ledger**. The default is one ledger in this process's memory, shared by every agent that names none — one per process even when an app loads both the CommonJS and the ESM build — so a server that builds an agent per request, or a pool that rebuilds an evicted instance, still answers each request once. It grows by one id per answered request for as long as the process runs, it does not survive a restart, and no other process sees it. When more than one process can resume the same paused run (replicas, a worker that picks up stored checkpoints, a process that restarts), give every agent that can resume it one ledger in a store they all reach, whose `spend(requestId)` is atomic:

```ts
const decisionLedger: DecisionLedger = {
  // true the first time, false after — a unique-key insert does this in one step
  spend: async (requestId) => (await db.insertIgnore('spent_requests', { requestId })) === 1,
  // optional: after a spend that threw, tells a host whether it landed — a pause
  // whose spend never landed stays answerable
  isSpent: async (requestId) => db.exists('spent_requests', { requestId }),
};
const agent = Agent.create({ provider, model, decisionLedger }).tool(issueRefund).build();
```

A ledger of an agent's own — even a fresh `inMemoryDecisionLedger()` — makes "once" hold for that ledger alone: agents given different ledgers spend separately. A refusal for an answered request (`'already-answered'`) says only what that resume knows: it ran nothing, and whether the earlier resume finished — so whether the call ran — is not known there.

A resume whose run is aborted — its caller hung up, or a deadline passed — never runs the call afterwards. The engine stops waiting on an aborted stage, but the stage goes on, so the run's signal is checked before the spend, after it, and once more at the last moment before the approved tool runs, after its credential (`needs`), its artifacts (`wants`) and the rest of an ask's chain resolve. Aborted before the spend, the decision is not spent and the pause can still be answered; aborted after it, the request is spent and its call never runs.

`by` is recorded as given: a claim, not proof. The binding says WHICH request and WHAT call; WHO may decide is your host's to authenticate. And the checkpoint itself is not proof either — a host that lets checkpoints leave its trust boundary signs them or keeps them server-side.

**What the binding detects, and what it does not.** It detects drift and replay: a checkpoint changed after the ask, a decision presented twice, to another pause, or to an agent whose rules after the ask changed. It does not defend against a hostile writer of the checkpoint store. Whoever can write the stored pause can rewrite the arguments together with the nonce and the request shown *before* the person decides — the person then approves what they were shown, and the binding holds — or switch the pause into a kind whose resume takes no decision at all (a credential-consent pause, which re-asks the identity provider and ignores the answer). Keep checkpoints server-side, or sign them, when the store is not trusted.

### A consent gate takes a decision, not a value

Resuming a check-in with anything that is not a `CheckInDecision` — a bare string, an object of your own shape, nothing at all — raises `DecisionRequiredError` (`code: 'ERR_DECISION_REQUIRED'`). **Nothing executes and the checkpoint is unchanged**, so you answer the same one properly and resume again. Over `standingAgent` it is a **400**: the session is fine, the request was not.

The error names which gate is outstanding (`gate: 'checkIn' | 'ask'`), the tool, the middleware that asked when it was an `ask`, and `received` — the *shape* that arrived, never its contents, because a resume payload is caller data and an error message ends up in logs.

Ask which kind of pause you are holding with `pauseDemandsDecision(outcome.pauseData)`: it returns a `ConsentGate` (`{ kind, toolName?, middleware? }`) for a check-in or a middleware `ask`, and `undefined` for a plain [`askHuman` / `pauseHere`](doc:pausable) pause — where the human's answer *is* the tool's result and any value is accepted. `ConsentGateKind` is the closed two-arm union that `kind` narrows to; a third consent gate would be a deliberate edit, never an arm that appears by surprise.

Before 8.13.0 a mis-shaped resume declined silently and filed the decision against `by: 'unknown'` — a consent record naming a person who was never asked. Governance never silently invents a decision, for the same reason it never silently drops one.

## Process A → checkpoint → Process B

Check-in rides the same JSON checkpoint machinery as [pause / resume](doc:pausable): the ask happens in one process, the human decides hours later, and a fresh agent resumes from the stored checkpoint. Build the agent fresh in Process B — only the checkpoint, the request the person was shown and their decision cross the boundary. Process B's default ledger never saw what Process A spent: if more than one process can resume it, give them one shared `decisionLedger` so the decision still runs once.

## Anti-patterns

- Don't reach into `outcome.pauseData` for a check-in — use `outcome.checkIn` (typed) and `isCheckInPause(outcome)`.
- Don't use `checkIn` as a policy engine. Policy is `permissionChecker` (deny/halt, no human); check-in is consent (a person decides). They compose — permission runs first.
- Don't resume a check-in pause with a bare string — pass a `CheckInDecision` (`checkInApproved` / `checkInDeclined`). Since 8.13.0 a malformed resume is refused with `DecisionRequiredError` rather than silently declined, so a consequential tool never runs by accident *and* you find out.
- Don't build a decision from anything but the request the person saw. `checkInApproved({ request: outcome.checkIn, by })` names that request; a decision hand-built without `requestId`, or kept from an earlier pause, is refused (`ResumeDecisionError`).
- Don't configure `.checkIn()` on an agent where no tool declares `checkIn` — that gate can never be consulted, and `build()` refuses it. `.checkIn()` decides HOW the ask is assembled; a tool's `checkIn: 'always'` (or a predicate) is what MAKES the ask.
- Don't pair `evidence: 'minimal'` with a `scorer`. The scorer ranks `drivers`, which the minimal pack does not build — `build()` refuses the pairing rather than resolving a scorer nothing will call.
- Don't put a `toolMiddleware` `ask` and a tool's own `checkIn` on the same call. They ask *different* questions — the rule's, and the tool's with the evidence pack attached — so approving one is not answering the other, and a resumed dispatch has no second checkpoint to ask on. Keep one gate per tool. (A *selective* `checkIn` whose predicate does not trip for those arguments is fine: since 8.13.0 the demand is evaluated, not merely noticed.)

## Run the demo

The flagship demo — **the coworker with the receipts** — is a runnable "AI coworker" that drafts a weekly status doc, saves it (a `save_draft` tool with **no** check-in — real work, no interruption), then reaches for the one consequential action: posting to the team channel. That `post_to_channel` tool declares `checkIn: 'always'`, so the run pauses and renders the receipts (`willDo` / `read` / `drivers` / `trail`) in your terminal.

```bash
# non-interactive approve (the tool runs)
npm run example examples/features/34-checkin-coworker.ts -- --approve

# non-interactive decline (watch the model adapt: it keeps the draft, posts nothing)
npm run example examples/features/34-checkin-coworker.ts -- --decline --note "not this week"

# interactive — a TTY prompts you to approve or decline
npm run example examples/features/34-checkin-coworker.ts

# real Claude instead of the deterministic $0 mock (only if ANTHROPIC_API_KEY is set)
npm run example examples/features/34-checkin-coworker.ts -- --live
```

The default provider is a deterministic mock, so it runs for anyone with zero setup; the end of the run prints the `CheckInRecorder` audit trail (asks + decisions with `by` / `note`).
